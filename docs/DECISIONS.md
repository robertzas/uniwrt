# Decisions

This is the index of accepted decisions (lightweight ADRs) and the open options awaiting the owner. Agents: read the tables, and open an entry only if your task touches it. When you have a new good idea, add it under "Open" with options and a recommended default, ask the owner, then move it to "Accepted".

| D-031 | **Core types and the store engine.** IDs are SQLite integers that the store assigns and never reuses (`AUTOINCREMENT`). `Timestamp` is Unix milliseconds (`i64`: a JSON number and an `INTEGER` column), shown as RFC 3339 only when displayed. MACs are stored as canonical text. Enum columns hold serde names without `CHECK` constraints, so a new variant needs no table rebuild. The store uses rusqlite with bundled SQLite and one writer thread that batches operations into a transaction, each in its own savepoint, with `synchronous=NORMAL`. Crates the agent adds follow the 7-day cooldown of D-029, transitive ones included (`just crate-age`), so rusqlite is 0.40.2 for now: 0.41.0 was 3 days old. `deny.toml` also allows Zlib, a permissive license compatible with MIT OR Apache-2.0 (foldhash, through rusqlite's statement cache). *Agent's call (reversible), M1.1.* | UUIDv7 or ULID IDs; jiff or chrono timestamps as RFC 3339 strings; MACs as integers; one transaction per write; `synchronous=FULL`; an r2d2 or deadpool pool; sqlx |
| D-032 | **SSH transport (M1.2).** russh 0.64 with the ring provider and **no RSA**: OpenWrt 24.10+ dropbear has ed25519 host keys and accepts ed25519 user keys, while the `rsa` crate carries an unfixed timing advisory (RUSTSEC-2023-0071); SSH certificates are never trusted. **Trust on first use is probe, then pin:** `probe` reads the host key without logging in, the user confirms the fingerprint, and every later connection checks the pin (`node_host_keys`); a mismatch quarantines the link until an admin re-trusts the node. **The vault is a stub until M1.6:** rows are marked `alg = 'plain'`, and M1.6 reseals them with XChaCha20-Poly1305. **Flow control:** russh stalls the whole connection while one channel's buffer is full, so each channel is drained by its own task, and a stream with more than 4 MiB of unread output ends with an overflow error. **Reconnects** use equal-jitter exponential backoff (1 s → 60 s), reset only after a connection stayed up 60 s. The agent restarts on the same connection with its own backoff, and commands keep working meanwhile (degraded mode). The agent envelope (ids, answers, events, ticks, hello, the protocol range) and its multiplexer moved from M1.3 into M1.2, because `NodeLink::call` needs them; M1.3 adds the ops. `deny.toml` also allows ISC, a permissive license compatible with MIT OR Apache-2.0 (ring and untrusted). *Agent's call (reversible), M1.2.* | aws-lc-rs (banned in deny.toml); RSA support; accepting certificates; trusting the first key without confirmation; known_hosts files; one byte budget per connection; full jitter; reconnecting SSH whenever the agent fails |
| D-033 | **Security-fix exception to the crate cooldown:** a crate younger than 7 days is allowed when it is the lowest release that fixes a RustSec advisory. It is listed with the advisory ID in `scripts/crate-age.sh` and removed once it ages out. First use: crypto-bigint 0.7.9 (RUSTSEC-2026-0387; 0.7.0–0.7.8 are yanked) and ctutils 0.4.6 (RUSTSEC-2026-0385, required by crypto-bigint 0.7.9), both through russh. *Owner's choice, M1.2.* | pausing the WP until the fix ages out (2026-11-01); a one-off exception |
| D-034 | **Node agent v0 (M1.3).** The agent is ucode with two loop modes. With ucode-mod-uloop, a forked `uloop.task` reads stdin with blocking reads (buffered reads on a non-blocking descriptor lose data) and feeds an event loop, and each `exec` runs in a task of its own. Without uloop (24.10 images without Wi-Fi), requests are served one at a time and the agent pushes nothing. Collect sets return raw sources (ubus replies, sysfs text, `/proc` files) and the `node` crate parses them, so the parsers are tested in Rust against captured fixtures and the agent stays small. Devices come from sysfs, which sees every kernel device, rather than from `network.device`. The bundle is an uncompressed tar embedded in the binary and installed by hash into `/tmp/uniwrt/agent`: `sha256sum -c` under a `flock`, and the hello must report that hash. *Agent's call (reversible), M1.3.* | the agent formatting facts itself; requiring uloop (no 24.10 wired nodes); `network.device status`; a gzipped bundle (needs a deflate crate) |
| D-035 | **Wireless and mesh collection, and the hwsim lab (M1.3b).** Wi-Fi state comes from nl80211 through ucode-mod-nl80211, which hostapd depends on, so every Wi-Fi image has it. It is joined with netifd's `network.wireless status` for the UCI view and hostapd's `get_clients` for what clients advertised; rpcd-mod-iwinfo is not needed. Radio hardware (`GET_WIPHY`, about 15 KB per phy even trimmed) is a set of its own, `phys` (`NodeFacts.phys`, replacing `RadioFacts.capabilities`), collected rarely, so `radios` and `stations` stay small enough for 2 s ticks. The agent keeps only the fields facts use where a source carries secrets (netifd's reply holds the Wi-Fi keys) or bulk; elsewhere it stays raw (D-034). Neighbors and the bridge FDB come from rtnetlink (ucode-mod-rtnl), or else from /proc/net/arp and `brforward`. Meshes are the devices of netifd's `proto batadv` interfaces, and devices with lower devices but no DEVTYPE (batman-adv sets none), confirmed by `batctl meshif <dev> mj` and read with batctl's JSON queries. 802.11r use is not reported yet: no source says whether a client associated with FT. Wireless fixtures come from the hwsim lab: mac80211_hwsim and batman-adv in the host's kernel, loaded and wired into the containers by a privileged helper container; local only. *Owner's choice (hwsim captures; privileged Docker for the root steps); the rest is the agent's call (reversible), M1.3b.* | rpcd-mod-iwinfo (needs LuCI; no DFS state or survey); parsing `iw` output; capabilities in every radio (the wiphy dump on every tick); spec-only fixtures until M1.7; a CI job for the lab (deferred); the owner running sudo |
| D-036 | **Agent streams (M1.3c).** The push ops need the event loop; without it they answer `unsupported` and the engine polls. **Topics** (`subscribe`/`unsubscribe`): `hostapd` (each BSS's object), `netifd` (`network.interface` and `network.device`, not the `network.interface.<name>` objects, which repeat the notifications) and `dhcp` (dnsmasq, odhcpd). An event is `<source>.<type>` with the daemon's data unchanged (D-034); `node::events` parses it into `model::event` and `model::log`. A ubus notification does not say which object sent it, so each object gets a subscriber of its own, and objects that appear (`ubus.object.add`) are subscribed to, so hostapd's survive `wifi reload`. The agent drops hostapd's probe requests. **Ticks** (`set_interval`): one timer per interval carries all of its sets, a set has one interval at a time, and intervals are at least 1 s. Sets are collected in the loop, as `collect` is, because forked tasks would share the ubus and netlink sockets. **Logs** (`log_follow`): by default logd is polled by id every second, which keeps sequence numbers and ms times and counts gaps as dropped. `stream` runs `logread -f -t -l <N+1>` in a task, which backfills and follows in one request to logd; the answer waits until logread follows, and logread is killed on stop and when the agent exits. That line count is the one value formatted into a shell string (`%d` of a checked integer), because `popen` takes no argv. hostapd's `sta-authorized` names the authentication algorithm, `ft` for an 802.11r fast transition: the source D-035 lacked. *Owner's choice (both log modes, polling by default); the rest is the agent's call (reversible), M1.3c.* | `logread -f` only; polling only; one subscriber per topic (cannot tell the objects apart); the per-interface netifd objects; ticks collected in forked tasks; backfilling a stream over ubus first (loses the lines logged before logread connects) |
| D-037 | **Engine (M1.4).** One actor per node (a tokio task, restarted with backoff if it panics) keeps the node's live facts and status, and sends its agent one request at a time, so an agent that serves requests one at a time is never asked twice at once. After each hello it subscribes to the topics, collects every set, then schedules ticks; an agent without an event loop, or one that refuses `set_interval`, is polled with `collect` on the same plan. **Intervals** are data (`Intervals`): 15 s for system, devices, interfaces, radios and stations; 30 s for neighbors and batman; 60 s for leases (DHCP events refresh them sooner); 1 h for capabilities and phys; board only when the agent starts. While the UI has a node open (`Engine::focus`, a guard), system, devices, radios and stations go to 2 s and batman to 10 s. A pushed event collects the set it touches again 500 ms later, and the events in that time share one collect. **Status:** offline while the link is not up (connecting, unreachable, quarantined); degraded while the agent is starting, failed or absent, a request or a set fails, or no telemetry arrived for three of the fastest intervals (at least 30 s), which also asks the agent for its pushes again, since it may have restarted unseen; else online. **Facts** are replaced, never mutated (readers hold `Arc`s), and `Event::Facts` goes out only when a set's part changed. **Roams:** a client authorized at another access point while it is still connected at the first, or within 15 s of leaving it; station lists seed the clients that joined before the engine watched. **Logs** are followed only while someone holds `Engine::follow_logs` (M2.5 decides whether storage holds one for every node); a follow that starts again after the agent restarts backfills 200 entries and skips those already announced. **Snapshots:** each node's latest facts, saved every 5 min when they changed and at shutdown. *Agent's call (reversible), M1.4.* | concurrent requests per node; one interval for every set; polling only; collecting only on the timer after events; a snapshot on every change (a write per node per tick); following every node's log all the time; roams from station lists only |

## Open (awaiting the owner's choice; the default applies until decided)

**O-1 · How to carve the 10.0.0.0/16 address space** (needed by M4.2)
- a) A /24 per network, with the third octet equal to the VLAN ID: LAN 10.0.0.0/24 (untagged), IoT 10.0.30.0/24, Guest 10.0.40.0/24. UniFi-like and easy to remember. ← *recommended*
- b) Flat: the LAN is the whole 10.0.0.0/16 (gateway 10.0.0.1), and extra networks live outside it.
- c) A larger LAN at 10.0.0.0/22 (1,022 hosts), with /24 VLANs at 10.0.<VLAN>.0 for VLAN IDs ≥ 4.

**O-2 · Client steering** (needed by M5.5)
- a) usteer with controller-managed profiles ← *recommended for phase 1*
- b) Controller-driven smart steering using global client history (phase 2, built on a)
- c) None; rely on 11k/v hints only

**O-3 · batman-adv routing algorithm** (needed by M5.3; M2 observe data can compare)
- a) BATMAN_IV: packet-loss metric, the most proven ← *recommended*
- b) BATMAN_V: throughput metric, better for mixed wired/wireless meshes when drivers report expected throughput

**O-4 · 32-bit ARM variants**
- a) armv7 (linux/arm/v7) only ← *recommended*
- b) Also armv6 (Raspberry Pi Zero/1, linux/arm/v6)

**O-5 · UI visual direction** (decided from rendered mockups at M1.8)
- a) "Midnight glass": dark, translucent layers, neon band accents
- b) "Graphite pro": neutral and crisp, Linear/Vercel-like ← *tentative*
- c) "UniFi-familiar": light and airy, blue accent

**O-6 · Extra distribution channels** (default: none until M9)
- a) An OpenWrt package for running the controller on an arm64/x86_64 gateway
- b) A Home Assistant add-on
- c) Unraid/TrueNAS templates and a Proxmox LXC

**O-7 · Optional AI troubleshooting assistant** (default: backlog)
An opt-in panel that explains incidents from logs, metrics and topology.
- a) Bring your own API key (for example, Claude)
- b) A local model (Ollama)
- c) Not at all

**O-8 · PPSK: per-device Wi-Fi passwords that map devices to VLANs** (default: backlog, after M5.1)

**O-9 · Home Assistant/MQTT integration: presence from client joins, alerts** (default: backlog)
