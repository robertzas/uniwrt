# Configuration lifecycle, upgrades & backups

Read this when working on desired state, revisions, render/diff/apply, drift, brownfield import, firmware upgrades, backups or node replacement.
Milestones: M3.1–M3.5, M7.1–M7.2.

## Desired state & revisions [M3.1] (D-065)

- The controller owns one typed document, `SiteConfig` (`crates/model/src/site/`): site settings (name, country, time zone, domain, NTP), the address plan (IPv4 space and ULA), networks (purpose, VLAN, IPv4 with DHCP and reservations, IPv6 mode, isolation, mDNS, IGMP snooping), WLANs (security, passphrase, bands, node scope), the mesh, the radio policy per band, the WAN (DHCP with client options, static, PPPoE, DS-Lite or IPv6 only; VLAN, 802.1p priority, MTU, MAC clone, IPv6 by DHCPv6 or 6rd, the ISP preset; features/wan.md), firewall policy overrides between networks, local DNS records, and per node its hostname, managed packages (D-011), radio overrides and raw UCI sections. A node's role stays on its inventory record. Schema v1 had every section with the fields M3.3 renders; later WPs extend them through migrations (`crates/model/src/site/migrate.rs`): v2 (M4.1) the WAN; v12 (M8.1a1, D-132) the upstream DNS, DDNS names and the NTP server (`services`).
- Networks and WLANs have ids (`[a-z][a-z0-9_]{0,11}`), which name their UCI sections (interfaces, zones, DHCP pools, `uw_<wlan>_<band>`), so they never change once created. A few are reserved for render's own (`loopback`, `wan`, `wan6`, `wan_6`, `bat0`, and the `uw_` prefix). Nodes are keyed by their id.
- **One linear history:** every save is an immutable revision (`revisions` table) with its author, time, message, schema and its structural diff from its parent (list items matched by key, so editing one network is one change at `networks/<id>/…`). A save names the revision it was edited from and is refused with 409 when another save came first. A save that changes nothing makes no revision. Restoring copies an older revision's document into a new revision. Discard (M3.4) is a restore of the last applied revision.
- **Validation** (`site::validate`): errors refuse a save (422 with issues by path); warnings come with the document. It enforces the IPAM guarantees (features/network.md), unique ids, names and VLANs, WLAN security rules (6 GHz needs WPA3 or OWE; PSK modes need a passphrase), channel and width per band, the WAN's fields, firewall cells, DNS names, and UCI identifiers in raw sections.
- **Secrets** are vault references, never values: each new value is sealed under a new name `config/<32 hex digits>` and committed with its revision, so an older revision (and a restore) still finds the value it had. A document may refer only to the secrets its parent or the revision it restores refers to, plus the ones committed with it. Values are checked (Wi-Fi and mesh keys 8–63 printable ASCII or a 64-hex PSK; PPPoE 1–128 characters).
- A new site starts from the defaults (revision 1): the 10.0.0.0/16 plan with a random ULA, the default LAN at 10.0.0.1/24 (DHCP .100–.249) with IPv6 from both the ULA and the delegated prefix (D-067), no WLANs, the mesh off, DHCP on the WAN, no country (a warning once radios broadcast). Nodes stay unmanaged, so nothing reaches them until management is enabled (M3.4, M3.5). Demo mode starts from the import of its simulated nodes instead (D-071, D-073; revision kind `import`): the LAN on 10.0.0.0/24 (D-108), the sim's SSID and its mesh on 5 GHz, and what the model can't hold as raw sections.
- Inheritance: site defaults → node group (later) → node overrides → per-node raw UCI sections (the validated escape hatch).
- Schema migrations (`site::migrate`) are forward-only steps on the JSON; revisions keep the schema they were written with and are upgraded when read. The tests upgrade a fixture of every schema (`crates/model/fixtures/site/v<n>.json`).
- API: `GET`/`PUT /api/v1/site`, `POST /api/v1/site/secrets/reveal` (admins; audited), `GET /api/v1/revisions` (pages), `GET /api/v1/revisions/{id}`, `GET /api/v1/revisions/{id}/diff?against=<id>`, `POST /api/v1/revisions/{id}/restore` (admins; audited).

## Ownership (D-011)

- For each node and each UCI package, the package is either **unmanaged** (observe only) or **managed** (rendered by the controller, which owns the whole file). The managed set grows feature by feature: network, wireless, dhcp, firewall, system, dropbear, usteer, sqm, wireguard, and so on.
- Unmanaged packages are never touched. Unknown sections inside a managed package survive only if brownfield import captured them as raw overrides.
- **Management mode [M3.4a1] (D-069):** a node starts in observe mode (directive 8) and is managed only once an admin turns management on for it (`PUT /api/v1/nodes/{id}/management`, `{"enabled":true}`; audited). The manage job logs in with the controller's key against the pinned host key, installs the footprint (the transaction tool `/etc/uniwrt/txn`, the guard `/etc/init.d/uniwrt-guard`, `/lib/upgrade/keep.d/uniwrt`) unless that version is there already, and records the node as managed. Turning management off removes the footprint and leaves the configuration as it is. An open transaction blocks both. Applies touch managed nodes only and list the others as skipped. The device page's Config tab (M3.4b1, D-071) turns management on and off (confirmed, the job followed live) and chooses the node's managed packages, each choice a revision.

## Render → diff → apply [M3.3–M3.4] (D-012, D-069, D-070)

The apply job (`crates/jobs/src/apply/`) applies the site's latest revision to every managed node: connect → plan → install (the feed packages a configuration needs and the node lacks, D-076; features/wan.md, Install step) → stage → apply → verify → confirm (→ settle, wan, channels and backhaul, the later rounds below) → record. API (admins): `GET /api/v1/apply/plan` (`ApplyPlan`: per node its action — change, unchanged, skipped in observe mode, or refused with its issues — the package diffs with secrets masked, the services switched, an address change, its hops and timer, in apply order), `POST /api/v1/apply` with `{"revision":<id>}` (the latest revision, the one reviewed; 409 otherwise; 202 with the job; audited), `GET /api/v1/apply/applied` (the revision each node holds; live over the WS topic `config`, with the latest revision, D-071). A job on several nodes keeps each node's state (`Job.nodes`: pending, unchanged, skipped, staged, applied, verified, confirmed, rolled back, failed) and its revision. A node renders only the packages its `managed` set lists (empty until chosen, D-011), so an apply leaves a node alone until then.

1. **Render** (pure, `crates/render`, D-067): `(SiteConfig, the vault's secret values, the node's role, NodeFacts, the node's current packages)` → its managed packages (`system`, `network`, `wireless`, `dhcp`, `firewall`, and on the gateway `sqm`, `mwan3` and `upnpd`; managing another is an error until it gets a renderer), the services to enable or disable, and warnings, or the issues that keep the node from rendering. Rendering depends on capabilities (switch kind, hostapd features, batman-adv) and the board's layout (board.json), not version strings.
   - Every node bridges all networks into `br-lan`: a plain bridge while every network is untagged (OpenWrt's stock shape), otherwise a VLAN-filtering bridge with each network's interface on `br-lan.<vid>`, Ethernet ports and `bat0` as trunks (the untagged network untagged, the others tagged) and Wi-Fi joining through its interface. On swconfig each VLAN is a `switch_vlan` tagged on the CPU port, whose `<cpu>.<vid>` devices join the bridge as access ports.
   - The gateway routes (a static interface per network, the WAN, dnsmasq, odhcpd, a firewall zone per network); its DHCP pools have `force '1'`, since dnsmasq's init otherwise refuses a segment where another server answers, such as an AP that still runs its stock one (D-068). APs bridge every port, the WAN port too, take a DHCP address on the management network (else the default one), and have dnsmasq, odhcpd and the firewall disabled, with firewall defaults that accept input.
   - Values the node generated for itself are carried over from its current packages: the DHCPv6 DUID (`network.globals.dhcp_default_duid`, which keeps the delegated prefix), the ULA prefix while the site sets none (`network.globals.ula_prefix`, which firstboot generated), `compat_version` when board.json has none, the board's `led` sections, and odhcpd's options other than `maindhcp`, `leasetrigger` and `loglevel` (its paths differ between releases).
   - The node's raw sections join their package last (a sealed value written as the vault holds it, D-073), replacing a rendered section of the same name; a raw *merge* (`merge: true`, D-072) instead sets its options on the rendered section of its name, or for an anonymous one the one of its type with the same key options (`uniwrt_render::raw::key`: a zone's `name`, a forwarding's `src` and `dest`, a host's `mac`; the first `dnsmasq`, `defaults` or `system`), and is left out with a warning once no section matches. A port that a raw `network` interface takes as its device (a wired batman-adv link) leaves the bridge.
   - Rendered packages hold secrets in option values (`key`, `password`): the review screen must mask them.
2. **Diff:** a semantic UCI diff (`uniwrt_uci::diff`: sections added, removed, changed or moved, option by option; order counts only among the sections of one type; D-066) against the node config, fetched fresh right before apply, shown on the review screen.
3. **Plan (fleet two-phase, D-069):** every managed node is logged in to and read at once (the tool's status, its packages and services with one command each, the agent's facts, and on the gateway its DNS), and every one must be reachable and plannable, or nothing changes. The nodes whose packages (a non-empty semantic diff) or services change are ordered leaves → gateway (by mesh and wired hops from the gateway in the topology the fresh facts describe). Every node is staged and checked before any applies; then all apply with their timers armed, then all are verified, then all are confirmed. A change that only works on every node at once (the management VLAN or subnet, the trunk ports, the mesh) therefore applies, which neither leaves-first nor gateway-first order allows node by node. Where the mesh's links drop, the nodes don't even reload one after another: they all reload at one instant (the synchronized cutover, D-114; features/wifi.md, RF planner: Apply).
4. **Apply** each node as a transaction (D-012) through the transaction tool (`node-agent/txn/txn`, run over exec; `uniwrt_node::txn`; a node whose tool is of another version than this controller's gets this one's before anything is staged, D-081):
   - `stage <id> <service>=on|off…` and `put <id> <package>` (the file on stdin) fill a stage in RAM (`/tmp/uniwrt/txn/<id>`); `check <id>` parses every staged package with `uci -c <stage> show` and checks that the services to start are installed. Nothing has changed yet.
   - `apply <id> <seconds>` snapshots the packages it replaces (or notes them absent) and the services' enablement to `/etc/uniwrt/journal/<id>/`, arms the dead-man timer (30 s – 1 h; default 120 s, longer for WAN and mesh changes, and `extend` keeps it alive while the other nodes apply), stops and disables the services that go off, installs each package atomically (keeping the file's mode), runs `fw4 check` when the firewall is staged (it reads only `/etc/config`, so it runs after install but before anything reloads, and a failure rolls back at once), enables the services that go on, and answers. `apply <id> <seconds> +<ms>` (`txn::apply_at`, D-114, the mesh's cutover) does the same, but stops the services that go off and reloads only `<ms>` (at most ten minutes) after the command started, counted on `/proc/uptime` (procd's reload instance sleeps through `ucode`, then logs `transaction <id> reloads as scheduled`); the deadline counts from then, the state stays `reloading` until it is done, and a rollback during the countdown restores files nothing has reloaded yet. Its answer carries the countdown left (`wait_ms`; 0 when the command came too late and the node reloaded at once). `apply <id> <seconds> <radio>…` (`txn::apply_live`, D-113) also writes each installed package's sum where `reload_config` keeps them (`/var/run/config.md5`), so nothing reloads them and netifd keeps running what it ran: the Channels round's channel switch moved the radios already; it journals the radios, and a rollback (not at boot) restarts each (`wifi down`, `wifi up`) on what the restored `wireless` says. procd then reloads (`reload_config`, then the services turned on start) in the guard's instance, which the SSH session dropping cannot stop; the state goes `applying` → `reloading` → `applied`.
   - Stop and disable the services that go off **before** `reload_config`: procd runs a service's reload triggers about a second later (`PROCD_RELOAD_DELAY`), and dnsmasq's reload starts it whether it is enabled or not; a stopped service has no triggers left. Health checks wait for the new config's own values (an address, a device), not just "up": until the triggers run, netifd still reports the old state (the system harness, M3.3b).
   - The dead-man timer is the guard's procd instance `txn wait <id>`, respawned if it dies; the deadline counts in uptime, so clock steps don't move it.
   - The controller verifies every node at once over a **new** SSH connection, at the address it moves to first, then its old one (only at the new one for a bridging gateway and for an access point asked to move, below; D-070: the gateway follows the network that holds its address; an AP stays while the management network's subnet holds its address, else takes its DHCP reservation, else the plan refuses it). It waits for `applied`, extends the timer, and checks health **against the baseline taken while planning**: what passed before must pass again (the gateway's WAN up with a default route and its dnsmasq resolving `localhost` and `openwrt.org`; radios up that were up and stay enabled; at least as many batman-adv neighbors); reaching the node is itself the check that the controller reaches it. It polls for up to 60 s (150 s after a WAN or mesh change), keeping the timers of the nodes already verified alive. Then it sends `confirm <id>` to each, leaves → gateway (accepted only once `applied`; `expired` once it rolled back).
   - Without a confirm, the node restores the snapshot, its services' enablement, reloads and restarts what it had stopped (`rolling_back`, then `rolled_back` with the reason `timeout`, `requested`, `invalid` or `boot`). After an unexpected reboot, `/etc/init.d/uniwrt-guard` (START=13: after logd, before the network) rolls back any unconfirmed transaction before the services start; a rollback cut short by a reboot runs again from the same snapshot.
5. **Record** the applied revision per node (`node_applied`, with the nodes found unchanged) and the managed packages each holds now (`node_config`, drift's baseline), and move each renumbered node's address and watch it there; the job is history, and a failed one an event and an alert (`job-failed`).

**Make-before-break (M4.3a2, D-081):** the gateway's part of an apply may be up to four transactions, each planned again from what the gateway holds then (`uniwrt_jobs::apply::{round, later}`), and the review shows the whole change with what will happen.
- **The network this controller sits on moves** (the gateway's view of the controller's login, `SSH_CONNECTION`, is inside a network whose new subnet doesn't hold it): the first transaction is the **bridge**. The network's interface keeps the old address after the new one (`list ipaddr`, new first: dnsmasq's pool follows the first) and its pool leases for 2 minutes; the timers are the long ones. Once the gateway has reloaded, each access point that moves renews its lease (`ubus call network.interface.<net> renew`) and is verified only at its reservation; then the tool's `bounce <seconds> <port>…` takes the bridge's Ethernet ports down for 3 s (detached from the login; never the WAN's or the mesh), so wired hosts ask again. Verify waits, within the uplink window (150 s), for a login that the gateway sees coming **from the new subnet**; then all confirm. The **Settle** step drops the old address and restores the lease time in a transaction of its own. A controller that keeps its address (a static one, or a host behind a switch whose lease isn't renewed by hand in time) fails verify: everything rolls back, and the rollback bounces the ports again so the hosts return. A controller outside the gateway's networks (routed, or over the WAN) has nothing moving under it: the apply follows the gateway to its new address as before.
- **The WAN changes among other things** (the `wan*` interfaces of `network` with the devices only they stand on, `uniwrt_render::wan_sections`, and the `sqm` and `mwan3` packages with their services): everything else applies and confirms first, then the **WAN** step applies the WAN alone. A WAN that changes alone is one transaction, as before.
- **Radios whose channels alone move** (M6.1 b1b, D-113; features/wifi.md, RF planner: Apply): a node whose change is only its radios' `channel`, `htmode` and `txpower`, on radios without the mesh, takes its power with the fleet's first transaction (a reload of power alone keeps hostapd running) and sits the other rounds out; the **Channels** step then moves its channels after the WAN's, one node at a time (stage, apply, switch, verify, confirm), live by a channel switch where every radio can announce it, else with a reload. A failure there rolls back that node alone and ends the apply partial; the nodes after it keep what they held.
- **Cables between nodes** (M5.3, D-097; features/mesh.md, Wired backhaul): the first transaction brings each new cable over as an overlay; the **Backhaul** step, last, probes them from both ends and then applies on every node with such a cable at once, each cable carrying the mesh alone or back to a trunk.
- A failure in a later transaction rolls back that transaction alone and ends the apply as `partial_apply`: the gateway stays behind the revision (`node_applied` keeps its old one, so the top bar still counts it), its packages are recorded as it holds them (drift's baseline), and applying again does only what is left.
- Limits: hosts behind a switch or on Wi-Fi don't see the bounce and keep their old lease until it renews (the old address is gone by then, so they are offline until they ask again; the plan warns, and M5 will deauthenticate stations); swconfig switches have no per-port devices to bounce. The demo's simulated gateway answers at its first address only, so a renumbering there rolls back (M4.3b).

**Review (M3.4b2, D-071):** the top bar counts the managed nodes the latest revision has yet to reach (never applied, or behind it; a node holding the revision the latest one restores counts as current, so discarding needs no apply) and opens `/changes`: the plan read fresh from the nodes (the impact in words, each node's diffs in apply order with secrets masked, the nodes refused or left alone), Apply (disabled while a node is refused or another revision was saved since the review), the job live per node, and **Discard changes**, which restores the newest revision a managed node holds as the next revision. Settings › Revisions restores any revision the same way; nothing reaches the nodes until it is reviewed and applied.

**Failure:** an unreachable or refused node fails the job before anything changes (`unreachable`, `refused`), as does one that refuses its stage (`node_failed`). A node that fails its apply or health checks stops the job before any confirm (`rolled_back`): the controller rolls back the nodes it applied (`rollback`, the gateway first), and any it cannot reach roll back at their deadline. A first confirm that fails rolls the rest back the same way; only one that fails after others succeeded (the node's timer ran out in between) leaves a partial apply (`partial_apply`): the rest still confirm, the job fails and alerts, and the user can keep the confirmed nodes, which stay consistent with their revision, or roll them back with the previous revision. Renumbering the network the controller itself sits on needs the controller to reach the new subnet within the timer (its own lease renews later): otherwise the apply rolls back, safely. Jobs don't resume (D-042): after a controller restart the unconfirmed nodes roll back by themselves.

## Drift [M3.5c] (D-072, D-074)

A managed package that changed on its node after the controller confirmed it, by anyone but the controller (LuCI, `uci set`, an editor), is **drift**. The backend is M3.5c1; the UI is M3.5c2: the device page's Config tab shows a managed node's drift with its actions, the top bar counts the drifts not acknowledged (admins; a popover links each to its device), the review marks the packages an apply overwrites, and `/settings/import?node=<id>&package=<name>` is the scoped import (ui.md).

- **Hashes:** the agent's `config` set (`node-agent/collect/config.uc`, every 60 s) reports each `/etc/config` file's SHA-256 as `sha256sum` prints it (`NodeFacts.config`). A file is hashed again only once its inode, size, mtime or ctime moved, so a tick costs a stat per file.
- **Baseline:** what the node holds once an apply confirms it: its managed packages as installed or kept (`node_config`; the nodes an apply finds unchanged too), replaced at every apply and forgotten when the node goes back to observe mode. Nothing is watched before a node's first apply, on observe-mode nodes, or in packages it doesn't manage.
- **Detection** (the engine's `DriftWatch`): a hash that isn't the baseline's has the file read over the agent's link and compared with `uniwrt_uci::diff`. Only a semantic change is drift; a file rewritten in another form becomes the baseline as it reads now. A drift keeps the node's file (or that it is gone) and shows its diff from the baseline, secrets masked; one that doesn't parse says so. A node is left alone while a job holds it; once the job ends its agent is asked for fresh hashes, and the drifts its apply confirmed anew end. The baselines are read again every minute.
- **Events and alerts:** a drift raises `config_drift` (warning; condition `node:<id>/drift:<package>`) and its end `config_drift_ended` (reverted, confirmed by an apply, acknowledged, muted, or no longer managed, with how long it lasted); the built-in rule `config-drift` alerts while one is raised.
- **What the user does** (admins; audited):
  - **Import** it into the model: `POST /api/v1/import/preview` with `{"drift": {"node", "package"}}` imports only that drift (Brownfield import below): every other package of every node is taken as the latest revision renders it, so the preview's changes are the drift's. Accepted like any import (`POST v1/import/accept`), then reviewed and applied, which confirms the package as the node holds it.
  - **Overwrite** it: the review (`/changes`) plans fresh, marks the node's drifted packages (`NodePlan.drift`), and the apply rewrites them.
  - **Acknowledge** it (`POST /api/v1/nodes/{id}/drift/{package}/acknowledge`): accepted as it is until the file changes again; its condition ends. The next apply still rewrites it.
  - **Mute** the package (`PUT /api/v1/nodes/{id}/drift/{package}/mute`, `{"muted": true}`): not watched until `false`; its drift ends.
- **API:** `GET /api/v1/drift` (`DriftState`: every drift and mute), live over the WS topic `config`.
- **Demo:** a minute after a simulated node's first confirmed apply, the sim edits one package that apply wrote by hand, once per node (`crates/sim/src/hand_edit.rs`): the hostname gets a `-1`, else the first radio's channel is pinned or set back to auto. Both are options render writes and the import reads, so the drift can be imported and overwritten alike.

## Brownfield import [M3.5] (D-072)

The import engine (`crates/import`, M3.5a) maps what the nodes hold into the site; the flow (M3.5b, D-073) reviews and saves it.

- **Input:** the site to start from, and per node its role, facts and UCI packages. **Output:** the site, the secrets found (Wi-Fi passphrases, the mesh key, the PPPoE password, for the caller to seal), and per node each section's fate, the residual, render's issues and a confidence score.
- **Site-wide parts from the gateway:** the time zone (`zonename`), NTP servers and local domain; networks (each `static` or `none` interface on the bridge, a `<bridge>.<vid>` device or a swconfig CPU port's VLAN device: VLAN, tagged as its trunk ports or switch ports tag it; address, with or without `netmask`; IPv6 from `ip6assign` and `ip6class`; the DHCP pool with OpenWrt's defaults; reservations from `host` sections); the ULA; local DNS (`domain`, `cname`); the WAN (DHCP, static or PPPoE; the ISP's VLAN from an 802.1Q device, `<port>.<vid>` or a tagged switch VLAN; a cloned MAC; IPv6); the firewall policy (zones named by their network, and each cell where the forwardings differ from what the purposes seed as an override). A network's purpose: Default for `lan` (else the first), else guessed from its name (guest, iot, mgmt), else Custom. The address space widens to hold the networks (their common prefix, at least a /16, if private). Without a gateway among the nodes, the site keeps these parts.
- **From every node:** WLANs (access points of the same SSID, network, security, key, hidden, isolation and state, on the bands and nodes that carry them; in the order the radios list them; ids from the site's WLAN of that SSID, a `uw_<id>_<band>` name, or the SSID), the mesh (an 802.11s point over a batman-adv hard interface), the radios (each band's most common channel, width and power among enabled radios as its policy, overrides for the others and for disabled radios), the country, and a hostname that differs from the node's own. Access points on a disabled radio are not WLANs.
- **Fitting each node:** its sections are renamed as render names them, rendered, and paired with the rendered ones by name or by their type's key. A paired section is the model's: the options render doesn't write are kept as a raw merge, so the site's edits still reach the section. An unpaired section is kept whole as a raw section; so is a WAN over a protocol the model lacks. An AP's firewall keeps only its defaults (the others are dropped: the firewall is off on APs). On an access point or a bridge, a router's parts are dropped too (the dumb AP, D-101): WAN interfaces (named `wan`, `wan6` or `wanb`, an IP uplink on the WAN port or a VLAN of it, IPv6 transition tunnels), 802.1Q devices on the WAN port, every DHCP server section but `dnsmasq` and `odhcpd`, a paired interface's addressing and a paired pool's settings; a batman-adv hard interface on the WAN port stays (a wired backhaul). A zone keeps holding the interfaces kept whole.
- **Invariant (lossless, D-072):** `render(import(x))` equals `x` under the semantic diff after the renames, up to the **residual**: the options render writes its own way (dnsmasq's `force`, every board port bridged, an AP's ULA), which the first apply would change. Nothing is lost beyond what render's design drops; values that mean the same (an address in another form, a boolean, an option or a one-item list) are no residual. Round-trip tests enforce it on the simulated fleet's hand-made configs, OpenWrt 24.10's and 25.12's stock ones, the hwsim gateway, and render's golden sites, which import exactly (nothing raw, no residual); importing an import's rendering gives the same site.
- **Confidence:** the share of the node's options the model holds; raw and kept options count against it.
- **Secrets in raw sections (D-073):** a raw option that holds a secret (`SECRET_OPTIONS`: Wi-Fi keys and RADIUS secrets, `password`, WireGuard's `private_key` and `preshared_key`) is kept as a vault reference (`{"secret": "config/…"}`), never in plain text; render writes the vault's value, review screens mask it, and an admin can reveal it at `nodes/<id>/raw/<i>/<option>` (audited).
- **Flow (M3.5b1; admins):** `POST /api/v1/import/preview` logs in to every adopted node (observe mode too; nothing changes on them), reads the packages render writes and the facts, imports them into the latest revision and seals the secrets found; it answers the `ImportPreview`: the site's changes (secrets as references), the imported document's issues, and per node its state (`imported`, `failed` with render's issues, or `unread` with why: not reached, an open transaction, a file that doesn't parse; an unread node keeps its settings), confidence, sections and their fate (mapped with the options kept raw, raw, dropped) and the residual (secrets masked). The controller holds the newest preview for 15 minutes; `POST /api/v1/import/accept` with `{"id", "message"}` saves exactly it as the next revision (kind `import`, audited): 404 once it isn't held, 409 if another revision was saved since, 422 while it has errors; one that changes nothing saves nothing. A found secret whose value the latest revision holds at the same path keeps its reference, so a re-import that finds nothing new changes nothing. Refused while an apply runs. Demo mode's first revision is the import of its simulated nodes.
- **UI (M3.5b2):** Settings › Import (`/settings/import`, admins) reads the nodes as it opens and shows the preview: the site's changes (secrets never shown), per node its state, confidence, sections by fate, the residual, and its warnings each once with a count (an import into nodes that manage nothing warns once per raw section); it accepts it with an optional message, then links to the review. Linked from Settings › Revisions, and from a banner on Devices while the latest revision is the defaults and nodes are adopted. The review (`/changes`) shows each node's raw overrides that the apply writes (`NodePlan.raw`: those of its managed packages).

## Firmware & rolling upgrades [M7.1] (D-015, D-121)

**Built (M7.1a1):** the **Updates** page lists every node's release (version, revision) and the upgrades on offer: the latest release of its branch (an *update*) and the next branch's latest (a *new release*), never skipping a branch, each with its release notes and the board's profile in that release (found by `supported_devices` in the download server's `profiles.json`, else the profile named like the board, else a target's only profile when it lists no board). **Built (M7.1a2b, D-122):** **GitHub releases** as image sources. Releases are read with GitHub's REST API (one page of 30, drafts left out) and kept 10 minutes per repo; a transport failure shows as a short note per row and is logged whole. A GitHub release's plan (`{"source": "github", "release": <tag>}`) lists its images and reads nothing from the node: it is flashed as it is. Audited (`firmware`).

**Built (M7.1b1, D-123):** the controller's **self-upgrade machinery**. *Release:* the newest release of `robertzas/uniwrt` tagged `vX.Y.Z` (not a prerelease) with a tarball for the binary's target and GitHub's SHA-256 of it. *Staging:* the tarball is streamed to `<data>/bin` (redirects followed, at most 96 MiB, 15 minutes) while hashed; its size and SHA-256 must match GitHub's; its **Sigstore attestation** (from GitHub's attestations API) must verify with uniwrt's own verifier against the embedded trust root (`just sigstore-root`): the Fulcio certificate chains to a Fulcio CA valid when Rekor logged the entry, for code signing, issued to `https://github.com/robertzas/uniwrt/.github/workflows/ci.yml@refs/heads/main` by `https://token.actions.githubusercontent.com`; the DSSE envelope's signature; the SLSA v1 statement naming the tarball and its SHA-256; Rekor v1's entry matching the envelope and certificate, its signed entry timestamp, and its inclusion proof up to a checkpoint the log signed. Only then is the binary extracted (`uniwrt-<version>-<target>/uniwrt`) as `bin/uniwrt-<version>`. *Running it:* the launcher (docs/dev/BUILD.md, Processes): a trial with the database snapshotted, confirmed healthy or rolled back with the database restored and the binary rejected for good; a newer image wins over a staged binary. The update notice, the install button and the opt-in nightly install come with b2.

**Built (M7.1b2, D-123):** the controller's **update notice and install**. The Updates page opens with a *Controller* card: the running version; the newest release for its target that is newer and hasn't failed a trial, with its date, size and release notes; for admins **Install**; why a controller can't install itself (a development build, demo mode, `--self-upgrade off`); the last release that failed its trial and why (rolled back, never offered again). An install runs in the background: downloading and verifying, then the new binary runs once (`version --json` must name the release and this target; a `noexec` data directory is named as the likely cause when it can't run), then it is named the trial in `bin/state.json` and the controller stops with exit code 75 so the launcher starts it. The card follows it through the restart (reads that fail meanwhile are expected, for up to 6 minutes) and ends with the new release running (and a *Reload* for its interface), rolled back, refused before the restart, or not back. **Automatic install** (opt-in, off by default): nightly in a one-hour window at the site's time (02:30 by default, before the RF optimizer's), the newest release out for at least a day (the button offers the newest), once a night, while no job runs; it waits within the window for running jobs and skips the night when GitHub can't be read. API: `GET v1/controller/update`, `POST v1/controller/update` (`{"version"}`: the release on offer; admins; 202; audited `controller`), `PUT v1/controller/update/settings` (`{"auto", "at_min"}`; admins; audited); the `controller_updates` setting.

**Built (M7.1c1, D-124):** **installing an upgrade on one node.** Once the dialog has a plan (and, for ASU, the finished build), an admin's **Install** on a managed node asks first (the node restarts and is offline for a few minutes, its settings kept and backed up; an official image's packages need internet afterwards), then starts the upgrade job and follows it in the dialog (also when it was started elsewhere); a node in observe mode says to turn management on. The job: **check** (the release the plan was made for, no open transaction, the image fitting its firmware and root file system, `/tmp` holding it with 16 MiB to spare; the health baseline: WAN and DNS on the gateway, radios up, mesh neighbors, clients, its log's error patterns of the last hour) → **backup** (`sysupgrade -b`, sealed on the controller) → **download** (into `<data>/images`, checked against the source's SHA-256 and size; kept for the next node, four at most) → **stage** (streamed into `/tmp`, its SHA-256 read back, `sysupgrade -T`) → **flash** (sysupgrade keeping the configuration) → **reboot** (down within 3 min, back within 10, with its pinned host key) → **install** (an official image's packages; failures are warnings) → **verify** (the release, the transaction tool, the baseline met again within 150 s) → **soak** (3 min, no new error patterns in its log) → **record** (its packages read again). A failure before the flash changes nothing; after it, the error says the new firmware is in and where the backup is; a node that doesn't come back gets recovery guidance. API: `POST v1/firmware/nodes/{id}/install` (`{"source": "asu", "release", "build"}`, `"official"`, `"upload"` or `"github"`, resolved by the controller from the plan's source; 202 with the job; audited `firmware`).

**Built (M7.1c2a, D-125):** **rolling upgrades**, engine and API. A rollout upgrades several managed nodes one at a time, each by c1's upgrade job: the canary (if any) first, then the nodes farthest from the gateway (hops in the topology of every adopted node's facts, as an apply orders them), the gateway last. Each node's image is the admin's choice from its offers (`{"source": "asu" | "official" | "github", "release"}` or `{"source": "upload", "sha256"}`), resolved at the node's turn as Install resolves it; ASU is asked for every build when the rollout starts, and at a node's turn the build is asked for again and waited for (up to 45 min). **Canary** (optional; 30 min to 24 h, 1 h by default in the UI): the first node upgraded soaks, then must have stayed online (no offline or reboot event), accept a login with its pinned key and run its release; else the rollout halts (resume goes on with the rest). **Window** (optional, daily in the site's time, 03:30–05:30 by default, at least 30 min, may cross midnight): nodes start only inside it; outside, the rollout waits for the next opening. A node's failure (its image, its job, observe mode) **halts** the rollout on it: **resume** tries it again, **skip** leaves it out; **pause** holds the next node (the running one finishes); **cancel** ends it while no node upgrades. Another job on the next node makes it retry every 30 s. The rollout is a stored record that its driver resumes after a controller restart (a node's job interrupted by the restart fails and halts the rollout on it); one at a time. API: `GET v1/firmware/rollouts` (latest 20), `GET …/rollouts/{id}`; admins: `POST v1/firmware/rollouts` (`{"nodes": [{"node", "choice"}], "canary": {"node"?, "soak_min"}, "window": {"start_min", "end_min"}}`, 202), `POST …/rollouts/{id}/pause`, `…/resume`, `…/cancel`, `…/rollouts/{id}/nodes/{node}/skip`; audited (`firmware`).

**Built (M7.1c2b, D-125):** the **pipeline UI**, the Updates page's *Rolling upgrades* card. An admin's **Roll out upgrades** (while no rollout is active) opens a dialog listing every device with an upgrade on offer: the managed ones with an OpenWrt upgrade preselected, a device in observe mode disabled with the reason; each chosen device has an image select (its GitHub releases, each OpenWrt release built by ASU or as the official image, newest first, its fitting uploads), preset to its newest offer from its own source, and its plan read and summed up (packages carried over, left out, `/tmp` short) with the whole plan a click away; start waits for every plan. Then the **expected order** (the canary first, the gateway last; the controller orders the rest by hops), the **canary** (on for 2+ devices: the farthest device unless picked, never the gateway; 30 min to 24 h, 1 h by default) and the **maintenance window** (off; 03:30–05:30 on the half hour when on; opening and closing must differ). *Upgrade N devices* asks first, then the card shows the rollout as the controller ordered it. **The live pipeline:** its state, canary soak and window, what it waits for (the canary until, the window's opening, another job), each device's place, image (`from → to`), state and detail, and the running (or failed) device's job steps from the `jobs` topic; a halt shows its error and what Resume and Skip do (after the canary's failed check, Resume goes on with the rest). Admins: **Pause** (running), **Resume**, **Skip** the failed device and **Cancel** (while no device upgrades), each but Pause confirmed. The rollout is read again every 3 s while it runs or a paused one finishes its device (no WS topic); its end or halt is toasted. **History:** the latest 20, each expandable to its pipeline as it ended.

- **Catalog:** OpenWrt releases (from `downloads.openwrt.org/.versions.json` and per-target `profiles.json`), each node's current version, available upgrades and links to release notes. Snapshot builds are opt-in.
- **Image source:**
  - Default: ASU (sysupgrade.openwrt.org or a self-hosted ASU) building the node's declarative package set (role + features + user extras), so the image has everything baked in.
  - Fallbacks: official images with packages installed after the upgrade, or an image the user uploads.
- **Verification:** the sha256 from ASU or `profiles.json`, `sysupgrade -T` on the node, a free-RAM check (the image is staged in `/tmp`), and board compatibility.
- **Rolling job:** leaves first (deepest in the mesh tree), gateway last. For each node:
  1. pre-checks, backup
  2. stage the image (streamed over SSH), verify it
  3. sysupgrade, keeping the config
  4. wait for the node to go down, then come back up (10 min timeout)
  5. re-push the agent and run post-checks: version, packages, mesh links, clients back, no new error log patterns
  6. soak (default 3 min), then move to the next node
- **On failure:** halt, with recovery guidance (failsafe mode, TFTP).
- **Options:** canary (one node, soak for N hours), maintenance window, pause/resume, skip a node.
- **Version paths:** 24.10 → 25.12 moves from opkg to apk; ASU images carry the package set. 23.05 → 25.12 requires two hops.

## Backups [M7.2] (with replace, D-054)

- **Nodes (M7.2a1, D-126):** a `sysupgrade -b` archive, sealed like a vault secret, taken at adoption, before every upgrade, before every apply (its Backup step, after the plan, for each node it changes; a node that can't be backed up stops it with nothing changed), weekly, and by an admin (*Back up now*). Weekly: Sundays at 03:00 site time (a 30-minute window) every online node, and on the other nights the online nodes whose newest backup is over 8 days old; one backup job a night (4 nodes at a time; one that fails doesn't stop the others; observe mode too: nothing changes on the node). Kept: the newest 10 per node, plus the adoption's always. A backup holding the same files as the node's newest (names, modes, links and contents; times aside, since `sysupgrade -b` writes touched files' mtimes) only sets that one's `seen_at`.
- **Restore onto the node (D-126):** managed nodes only; the backup's `/etc/config` packages that differ from the node's go back as one transaction: check (no open transaction, each package parses) → backup (what it holds now, reason `restore`) → stage → apply (the uplink's dead-man timer) → verify (a new login at its address, as healthy as before within the uplink's verify time, else rolled back at once or by its timer) → confirm. The archive's other files (passwords, host keys, scripts) are not restored; an admin can download it for `sysupgrade -r`. Afterwards the node differs from the site's revision until the next apply (drift shows it).
- **API:** `GET v1/nodes/{id}/backups` (newest first); admins: `POST` it (a job), `GET …/backups/{backup}/archive` (the tarball, audited), `POST …/backups/{backup}/restore` (a job, audited; 409 in observe mode).
- **UI (M7.2a1b):** the device page's Config tab has a Backups card: the list, newest first (taken, why, size, unchanged since), and for admins *Back up now*, *Download* and, on managed nodes, *Restore* after a confirmation that says what comes back and what doesn't. Running backup and restore jobs that touch the node show their steps; the list is read again as each ends.
- **Controller (M7.2a2, D-129):** an [age](https://age-encryption.org) file (one passphrase, scrypt) of a gzip tarball holding `uniwrt-backup.json` (format, version, schema, time), `master.key` and `uniwrt.db` (an online `VACUUM INTO`: the vault, the certificates and all history are in it). It opens without uniwrt: `age -d uniwrt-backup-….tar.gz.age | tar xz` in a stopped controller's data directory restores it by hand. Taken nightly at 02:00 site time (30 minutes, before the controller's own update and the node backups) once an admin has set the passphrase (at least 12 characters, sealed in the vault), and by an admin (*Back up now*); written to `<data>/backups` and copied to `--backup-dir` (`UNIWRT_BACKUP_DIR`, a NAS mount), the newest 7 in each. Firmware uploads and the image cache are not in it.
- **Controller restore (D-129):** from Settings, from the first-run screen of a new host (while setup is open), or with `uniwrt restore FILE` (the passphrase from `UNIWRT_BACKUP_PASSPHRASE` or stdin). The file is decrypted and checked whole first (a wrong passphrase, a cut or altered file, a newer uniwrt's schema, a key that doesn't open its vault are refused) and staged in `<data>/restore`; the controller then restarts (under the launcher, or the container's restart policy: run it with `--restart unless-stopped`), and the start puts the backup in place before it opens the database, keeping what it replaced in `<data>/restore/previous` until the next restore. A host with its own key (`UNIWRT_MASTER_KEY`, or a `--master-key-file` that exists) keeps it and the restored secrets are resealed under it; otherwise the backup's key becomes the key file.
- **Controller API:** `GET v1/controller/backups` (the passphrase's presence, the directories, the backups newest first, whether one runs, how the last went, the staged restore); admins: `POST` it (201 once taken), `GET …/backups/{name}` (the file, `no-store`, audited), `PUT …/backups/passphrase`; an admin or, during first-run setup, anyone: `GET`/`PUT`/`DELETE v1/controller/restore` (the state, the upload, discard), `POST …/restore/unlock` (`{passphrase}`), `POST …/restore/apply` (202: restarts). Audited (`backup`).
- **Controller UI (M7.2a2b):** Settings → Backups: the backups newest first (taken, size, file name, *Copied* where `--backup-dir` is set), how the last went, where they are kept, a warning while no passphrase is set; admins: *Back up now*, *Download*, the Passphrase card (12+ characters, confirmed) and *Restore from a file…*. The restore dialog uploads the file, opens it with its passphrase, shows what it holds and what it replaces, then *Restore and restart*; the page follows the restart and reloads when the controller is back. The first-run screen offers the same restore under the setup form.
- **Site export/import (M7.2a3, D-130)** as JSON, for migration or config-as-code (`uniwrt_model::site::export`): `{"format": "uniwrt-site", "version": 1, "exported_at", "uniwrt", "revision", "nodes", "config", "secrets"}`, pretty-printed. `config` is the latest revision's document as stored (its secret slots hold their vault references, which an import reads only as "set"); `nodes` names each node it has overrides for by MAC and name (overrides of a node no longer adopted are left out). `secrets` is `null` or an armored age file (one scrypt passphrase stanza, `uniwrt_store::age::armor`) of a JSON object of path → value: `jq -r .secrets FILE | age -d` opens it.
- **Site import:** an older schema is upgraded, a newer one or a newer format refused. Each node of the file maps onto the adopted node with its MAC; one with no match is dropped with its overrides; an adopted node the file doesn't name keeps the latest revision's overrides. Each secret slot the file sets takes the file's value (checked as a save checks it; the latest revision's reference when the value is the same), else the latest revision's secret at the same path (*kept*), else nothing (*missing*: a PSK WLAN then fails validation until a value is given on accept). A file with secrets imports without the passphrase too (they count as absent); a wrong passphrase is refused. Nothing reaches a node until the revision is applied; node modes are untouched.
- **Site file API:** `GET v1/site/export` (the file without secrets, an attachment `uniwrt-site-r<rev>.json`; any session); admins: `POST v1/site/export` with `{passphrase}` (12+ characters; audited as revealing secrets), `POST v1/site/import/preview` with `{file, passphrase?}` (the `SiteImportPreview`: changes, issues, the node mapping, each secret's source; held 15 minutes, apart from the brownfield import's), `POST v1/site/import/accept` with `{id, message?, secrets?}` (the next revision, kind `file`; 404 once not held, 409 after another save, 422 with errors, the preview kept; audited).
- **Site file UI (M7.2a3b):** Settings › Revisions has *Export* for every session: a dialog that downloads the file without secrets or, for admins, with them under a passphrase typed twice (12+ characters). Admins get *Import a file*, its own page (`/settings/import/file`, beside the brownfield import): the file is read in the browser and refused there unless it is JSON with `format: "uniwrt-site"`; one holding secrets asks for the passphrase (empty imports without them); *Preview* shows the file's revision, uniwrt version and export time, the changes, the warnings and errors, the devices of the file and the adopted one each takes by MAC (or none: its settings are left out), the adopted ones it doesn't name (they keep theirs), and each secret's source with a password field for each missing one. An error on a missing secret blocks *Accept* until a value is typed (the accept checks the value: its 422 shows at the field, the preview kept); other errors block it outright. A preview whose secrets weren't opened offers *Enter the passphrase* (the file stays picked); one made stale by another save says so and offers *Preview again*, which an expired or stale accept does by itself. Accepted, it links to Review changes and Revisions.

## Replace / RMA / decommission [M7.2] (D-131)

- **Replace (M7.2b1b):** the new device (any model) takes over the failed node's record: the same node id, so its name, role, overrides, floor placement, firmware source, DHCP reservation (its MAC rewritten) and history (charts, timeline, backups) carry on, while MAC, board, address, host key, facts and inventory become the new device's (`replace_node`, one write; what the controller knew of the old device's configuration, its drift, mutes and last apply, goes). A job (`replace`) runs the adoption's steps against the new device (Path A: address, confirmed host key, password), then its Record step takes the record over and commits a revision of kind `replace` (*Replaced <name>'s device*, by the admin; only when something changed) made by `site::replace::replace_node`: radio overrides and the RF plan follow the band (the n-th radio of a band on the old device becomes the n-th of that band on the new one; a radio the old facts never listed stays only under its own name and band), port profiles the port's name (render's `port_names`: Ethernet devices and `switch0:N`), reservations the new MAC; the node's raw sections go (they described the old device's own configuration; Manage imports the new device's), its managed packages and hostname stay. The step lists what had no match, and Review shows the revision's diff before any apply: that is the preview. The node is in observe mode; management and an apply follow. Timeline: *<name>'s device replaced* (`node_replaced`). The gateway may be replaced. The device must not be adopted as another node (`already_adopted`).
- **Factory reset & re-adopt (M7.2b1b):** a job (`reset`): connect → remove the transaction tool → wipe with `firstboot` (as a decommission does) → record: a pre-approval of the node's MAC and board tied to the node (`ZtpApproval.node`, `board_name`; it never expires, `expires_at` the end of 9999), and the node is watched again (it shows offline). Any adoption path that then finds that MAC (the ZTP hello, the adoption port, discovery, a manual adoption or the one-liner's hello) treats the record as not adopted and adopts the device back into it: the adoption's Check step finds the approval (another board fails with `identity_mismatch`), and the Record step takes the record over as a replace does (the same device: nothing to remap, so usually no revision); the approval goes with that write, so a failed adoption leaves it for the next try. Withdrawing the approval (the ZTP card lists it as *Reset; … never expires*) ends the wait; the record stays, offline. Refused for the gateway while other nodes are adopted. Timeline: *<name> reset to its defaults* (`node_reset`).
- **Decommission (M7.2b1a):** a job: connect → remove the transaction tool (`txn uninstall`; refused while a transaction is open; the node counts as observed from then on) → wipe → record. The wipe stops the controller watching the node, then runs on it detached from the login (`uniwrt_node::decommission`; leaving the mesh may cut it), a second after answering `started`: the ZTP hello and the guard disabled and removed, `/etc/uniwrt`, `/tmp/uniwrt` and the controller's `authorized_keys` line gone; then either `firstboot -y && reboot` (opt-in) or the mesh left (every `wifi-iface` in `mode mesh` and every `batadv_hardif` interface deleted, `reload_config`), the node's other settings kept. Nothing reports back (the controller's key is gone). A failure before the wipe starts watching the node again. Without `firstboot` the node keeps the root password the controller set, which goes from the vault with the record: the UI shows it before.
- **Forget (M7.2b1a):** the record step alone, for a node that can't be reached: nothing changes on it.
- **Record (both):** the controller stops watching the node; when the latest revision names it (its overrides, WLAN scopes, the RF plan, DHCP reservations of its MAC), a revision of kind `remove` (*Removed <name>*, by the admin) leaves it out, which needs no apply for the others; then the record goes with everything stored about it (its tables, metric series, pinned topology place, vault secrets `node/<id>/…`, firmware source). The timeline, logs, jobs and client history stay, and the timeline gets *<name> decommissioned* or *forgotten* (`node_removed`). Node ids are never reused.
- **Rules:** both hold the node and the site's configuration (no apply runs meanwhile); refused for the gateway while other nodes are adopted (replace it instead) and for a node an active rollout still has to upgrade (skip it there or cancel the rollout).
- **API:** admins: `POST v1/nodes/{id}/decommission` with `{firstboot}` and `DELETE v1/nodes/{id}` (forget), audited `decommission`; `POST v1/nodes/{id}/replace` with `{host, port?, host_key, password?, remember_password?}` (as `POST v1/adopt`, without name and role) and `POST v1/nodes/{id}/reset`, audited `replace`. Each answers 202 with the job, 409 when refused (a rollout still to upgrade the node, a running apply or job for it; reset, decommission and forget also for the gateway with others adopted).
- **UI (M7.2b2):** admins get a *Replace or remove* card on the device page's Config tab, with each action's consequence and a button opening its dialog; while other devices are adopted, only *Replace* is offered for the gateway. **Replace** runs the adopt wizard's steps (address and password, then the probed fingerprint to confirm, then the job's steps). The Record step's detail lists what found no match, and on success *Review changes* opens `/changes` (the node stays in observe mode until management is turned on). **Reset** names the MAC and board the record waits for. **Decommission** offers `firstboot` (off by default) and, without it, the root password to note down first (revealed on demand and audited, as on the Root password card). **Forget** says nothing changes on the device. Each dialog follows its job and shows the server's 409 refusal as it is worded. Once a decommission or forget deletes the record, the device page shows that job's steps and outcome in place of *Device not found* (`removalOf` over the `jobs` topic). An offline node whose record awaits its device (an approval in `v1/ztp/pending` with its `node`) shows *Waiting for its device* above the tabs, with the MAC and board and how the device comes back: a uniwrt image calls home by itself; a stock image is found through the site's adoption port (the port named) or, without one, is adopted by hand at 192.168.1.1. *Stop waiting* withdraws the approval.
