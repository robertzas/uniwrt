# Networks, addressing & gateway services

Read this when working on IPAM, networks/VLANs, DHCP/DNS, IPv6, the firewall, VPN or other gateway services.
Milestones: M4.2 (IPAM, networks, firewall), M8.1 (services), M8.2 (VPN).

## Address plan (IPAM)

The site address space defaults to **10.0.0.0/16** and is configurable at first run (any RFC 1918 range, plus a ULA for IPv6).
Each network gets a /24 whose third octet is its VLAN ID (D-077); a VLAN with no third octet in the space takes the first free /24. The suggestions (`uniwrt_model::site::ipam`, `GET v1/ipam/network`, `GET v1/ipam/reservation`) only propose: any subnet that validates may be typed.

| Network | VLAN | Subnet | Gateway | Notes |
|---|---|---|---|---|
| Default (LAN) | untagged | 10.0.0.0/24 | 10.0.0.1 | .2–.31 infrastructure (nodes, controller) · .32–.99 static reservations · .100–.249 DHCP pool |
| IoT | 30 | 10.0.30.0/24 | 10.0.30.1 | Internet allowed; blocked from the LAN |
| Guest | 40 | 10.0.40.0/24 | 10.0.40.1 | Internet only; client isolation |
| Management (optional) | 99 | 10.0.99.0/24 | 10.0.99.1 | Moves nodes off the user LAN |

Usual VLANs: IoT 30, Guest 40, Management 99, others 50, 60, … (the next free one when taken). "Fix IP" keeps the client's current address when no reservation has it, else takes the first free one of .32–.99.

IPAM guarantees:
- No overlapping subnets; gateways and pools sit inside their subnet; reservations are unique (validation).
- No collision with the WAN side: CGNAT 100.64.0.0/10 and a static WAN's subnet (validation), and the subnet the gateway's uplinks hold now, such as an ISP modem's (render refuses the plan).
- 192.168.1.0/24 stays free for adopting factory-default devices (a warning).

## Networks

Fields:
- name; purpose (default | iot | guest | mgmt | custom); VLAN
- IPv4: subnet, DHCP pool, lease time, reservations, options (DNS and NTP servers, domain, PXE boot, custom `<code>,<value>`)
- IPv6: off | ULA | delegated | both (the hint is the VLAN ID); how clients get addresses: SLAAC only, SLAAC with stateless DHCPv6 (default), SLAAC and stateful DHCPv6 (as OpenWrt ships), stateful DHCPv6 only (Android gets no address)
- inter-network policy (see Firewall) and client isolation
- mDNS reflection membership and IGMP snooping

Port profiles (per node, D-077): an Ethernet port carries one network untagged (its native network, or none) and tagged ones (all with a VLAN, none, or a list), and says whether the mesh's wired backhaul may take it over (`backhaul`, default yes; mesh.md, Wired backhaul). A port without a profile is a trunk: the untagged network untagged, every VLAN tagged. The Ports tab lists an AP's or a bridge's WAN port last, as one more LAN port (D-157). Ports are named by device (`lan2`, `eth1`) or, on a swconfig switch, by number (`switch0:3`). The untagged network is never tagged.

Rendering:
- **Every node [M3.3]:** one bridge, `br-lan`, carries every network (D-067). With VLAN networks it filters VLANs: a `bridge-vlan` per network (the untagged network gets the lowest free VLAN ID inside the bridge), each network's interface on `br-lan.<vid>`, Ethernet ports as their profiles say (trunks by default), `bat0` always a trunk, Wi-Fi joining through its interface. A swconfig switch gets a `switch_vlan` per network, tagged on the CPU port, its user ports as their profiles say, and the CPU port's `<cpu>.<vid>` devices join the bridge as access ports. A port that carries nothing leaves the bridge (on a switch, every VLAN). Profiles naming a port the node lacks, its WAN port or one the backup line or a raw interface takes are left out with a warning; on an AP, a linked port that would drop the node's own network warns (the apply's rollback catches a lost uplink).
- **Gateway:** one static `interface` per network (`list ipaddr`, `ip6assign 64`, `ip6hint` = VLAN ID in hex, `ip6class` `local` for ULA-only or the delegating interface for delegated-only); dnsmasq `dhcp` sections with the pool as `start`/`limit` and the options as `list dhcp_option` (6, 42, 15, then custom), PXE as a `boot` section keyed by `networkid`; odhcpd per the clients mode (`dhcpv6`, `ra_slaac`, `ra_flags`); reservations as `host`, records as `domain` and `cname`.
- **Creating one** [M9.6c, D-157; the owner's choice: guidance, no new checks]: the editor of a new network says under *What applying it does* that saving changes nothing until applied, that the gateway and the managed APs apply together and a device the controller can't reach again rolls back by itself (the whole apply with it), and, as they apply, that the site's first VLAN turns on the bridges' VLAN filtering (a short network restart on each device), that ports without settings carry the VLAN tagged (a switch between devices must pass it; devices behind one that doesn't keep the default network and the controller), and that a management network moves the APs' management addresses (reached through the gateway; unreachable ones roll the apply back). The review already gives each device's rollback timer; the guide (networks.md, *What happens when you apply a new network*) adds recovering by hand.
- **APs:** layer 2 only. Every port is bridged, the WAN port too. Management uses a DHCP client on the management network, else the default one; the other networks are `proto none`.
- Bridge-wide in v1: IGMP snooping is on when any network asks for it. Client isolation renders on the network's WLANs (`isolate`) and, for the untagged network, as batman's `ap_isolation`; wired isolation and per-VLAN batman isolation come later. mDNS reflection needs M8.1's services.

## DHCP & local DNS

- dnsmasq on the gateway: pools, reservations (created with "Fix IP" on the Clients page) and options (NTP, DNS, domain, PXE). Lease events stream to the controller and feed the client inventory.
- Local DNS: `<hostname>.lan` is automatic, plus custom A/AAAA/CNAME records. `uniwrt.<domain>` points at the controller: an apply reads the controller's address from the gateway's `SSH_CONNECTION` and renders a `domain` record `uniwrt` when that address sits in one of the networks; a custom record can't take the name.
- **Upstream DNS** [M8.1a1, D-132; layers M9.0b1, D-146] (`services.upstream`, schema v12, layered in v20): ordered **layers**, each optional and tried in a fixed order: up to 4 **encrypted resolvers** (DNS over HTTPS or over TLS, mixed, in the order given), then up to 4 **plain servers** (IPv4 or IPv6), then the **ISP's** (the WAN's servers, as OpenWrt ships). **Strict** (off by default; needs an encrypted resolver) keeps queries on the encrypted layer alone: the plain layers stay in the site but are left out. At least one layer must be in effect. dnsmasq forwards to each encrypted resolver's local proxy, then the plain servers (`server` lines), then the resolv file (`noresolv` while the ISP's are off); with more than one layer it asks them in order (`strictorder`), so a later layer hears a query only after the earlier ones refused it, failed it (SERVFAIL) or let the client's retry come; within a single layer dnsmasq keeps choosing the fastest server, which routes around a dead one. **DoH** runs through https-dns-proxy: each resolver an `https://` URL with 2 to 4 plain bootstrap servers (none where the host is an address: the proxy's own list then; one alone makes the proxy abort), its own instance on `127.0.0.1` from port 5053 (in the order of the DoH resolvers). **DoT** runs through **stubby**, one daemon on `127.0.0.1#5453` holding every DoT resolver (its certificate's name, 1 to 4 addresses asked in order, a port, 853 as a rule, and up to 4 SPKI pins, the base64 SHA-256 of its public key, checked besides the certificate), asked in order (`round_robin_upstreams '0'`), TLS only with authentication required, padding on, answering SERVFAIL after 2 s so dnsmasq moves on at once; the DoT resolvers sit next to each other in the list (stubby is asked in the first one's place). Failover costs differ (REFERENCE ⚠️ on hardware): a DoT resolver that stopped answering costs a query up to 2 s, a DoH one the client's retry (~1–5 s), as https-dns-proxy never answers a failed query. The proxies never touch dnsmasq or the firewall (`dnsmasq_config_update '-'`, `force_dns '0'`; render owns both), https-dns-proxy's canary domains and heartbeat are off, and the NTP servers' names resolve through a plain server while TLS needs the right time first: DoH's first bootstrap server (IPv4 first), else, while strict, the first DoT address (the public DoT services answer plain DNS on port 53 too); without DoH and not strict a TLS failure moves those names to the plain layers anyway. The services set reports the running proxies (`doh_instances`, `dot_instances`). Import maps dnsmasq's servers back where they are the model's in its order (local proxies first, by port, then plain servers; with the ISP's on, only under `strictorder`), stubby's consecutive resolver sections with the same name, port and pins as one resolver; anything else stays the ISP's (its options raw). The UI [M9.0b2] edits the layers in one card: encrypted resolvers as rows, each DoH or DoT from presets (Cloudflare, Quad9, Google, NextDNS with its profile id, AdGuard; DoH filling URL and bootstrap servers, DoT the certificate's name and two addresses on port 853, no key pins) or custom, moved up and down with the DoT rows kept together; then up to 4 plain servers, *Then the ISP's servers* and *Encrypted only* (the kept layers marked *Not asked*). The summary lists the layers in order and the proxies the gateway runs (DoH instances against the DoH resolvers, stubby when any DoT). APs keep dnsmasq off and forward nothing.
- **Per-network DNS:** a pool hands out other DNS servers (option 6) instead of the gateway (M4.2a); blocklist bypass per client is a firewall redirect (below).
- **Blocklists** [M8.1a2, D-132, D-133] (`services.blocking`, schema v13; off by default): lists from a curated catalog (ads and trackers: HaGeZi Light/Normal/Pro, OISD Small/Big, StevenBlack; malware: URLhaus, Phishing Filter, HaGeZi Threat Intelligence Mini; turning blocking on starts from HaGeZi Normal + URLhaus) and up to 16 custom URLs (hosts, plain domains, adblock `||domain^` or dnsmasq lines), plus up to 1,000 allowed and 1,000 blocked domains (each with its subdomains). The controller downloads them nightly (in the site's 04:00–06:00 window once the oldest copy is about 20 h old, at any time past 48 h, at once for a list never fetched) and on demand (`POST v1/services/blocklists/refresh`), keeping the last good copy of each, deduplicates them and compiles one `servers-file` (`server=/domain/` blocks, `server=/domain/#` re-allows under a blocked parent; capped at an eighth of the gateway's memory, the user's own blocks and the malware lists kept first). The gateway gets the settings of the revision **applied** to it (list choices, allow and deny reach it with an apply; refreshed list content without one), and only while that revision manages its `dhcp`: the controller compares the SHA-256 in the file's header line, which the gateway's `services` set reports, with its compile, and pushes on a mismatch while the gateway is online and no job holds it. `GET v1/services/blocklists` shows the catalog, each list's download state, the compile (domains, cut, capacity) and the gateway's copy (synced, pushing, failed, waiting, offline, busy, off or unmanaged). While blocking is on, the gateway's main dnsmasq reads `*.conf` from `/tmp/dnsmasq.uniwrt.d`, where the push writes the list and the conf file that loads it; a refresh is read again on SIGHUP. Until the first push, and after a reboot until the controller pushes again, dnsmasq resolves unfiltered (it can't start with a missing servers-file). **UI** (M8.1a2b1): `/networks` has a DNS filtering card beside upstream DNS: the gateway's copy (synced with its domain count, pushing, failed with the error, offline, …), a note while the saved settings wait for an apply, the compile's cut against the gateway's capacity, figures (domains blocked, lists, allowed domains, bypassing clients) and each list's download state; the state is read every 3 s while lists download or go out, else every 30 s. Admins refresh the lists and edit the settings in a dialog: on/off (turning it on with nothing to block starts from the default lists), the catalog by category with each list's size and the chosen total against the capacity, custom lists, allowed and blocked domains one per line (lowercased, `*.` dropped, checked as the model checks them), bypassing clients picked by name or typed MAC, and query statistics.
- **Bypass** (per client, by MAC): the firewall redirects the client's DNS (port 53, TCP and UDP, IPv4 and IPv6, in every network's zone: `uniwrt_dns_bypass_<network>`) to a second dnsmasq instance on port 5354 with the same upstream (DoH included), which asks the main instance for local names. The instances are then named `main` and `unfiltered`, and the pools name `main` (`option instance`), so only the main one serves DHCP.
- **Query statistics** [M8.1a2a2, D-133] (`services.blocking.stats`, schema v14; on, and in effect while blocking is): both dnsmasq instances log every query (`logqueries`, which OpenWrt 24.10 and 25.12 pass as `--log-queries=extra`: each line carries the query's serial and the client's address) and the gateway's log buffer grows to 256 KiB. The lines reach the controller with the rest of the log (the agent, or syslog) but are never stored as log entries: they go to the statistics through a queue of their own (8,192 lines; syslog gives them their own rate per sender and at most half its queue). Each query is paired with its answer line (by serial; in the plain form, the line after it): forwarded, cached, local (hosts files, leases, configured names), blocked (`config <name> is NXDOMAIN` for a name of two labels or more, not a reverse lookup and not under the site's local domain) or failed (`REFUSED`/`SERVFAIL`); a query with no answer line (it joined one in flight) counts as forwarded after 5 s. Queries from the gateway itself (loopback) are left out, and a query at or below the highest serial seen of its dnsmasq process (the agent's backfill, or syslog and the agent both delivering it) is skipped. The client is named by the MAC of the client holding its address, else by the address. The controller keeps 24 h of queries and 30 days of hourly counts per client (queries, blocked), stored every 2 s; top domains and top blocked are read from the queries. The API (M8.1a2a2b) serves `GET v1/services/dns/stats?range=24h|7d|30d` (the range's totals, its hourly series summed over clients, each client's totals named by its alias or DHCP hostname, by MAC or by the client now holding the address, and the 20 top answered and top blocked domains of the last 24 h, through a covering index on outcome and domain) and `GET v1/services/dns/queries` (newest first, filtered by client (a MAC, or the address of a client no MAC was known for), outcome and domain text, a page of up to 1,000 at a time with a `<time>:<id>` cursor). The demo's gateway logs queries while its `dhcp` sets `logqueries`: popular names, local ones and names of the blocklist it was pushed, the bypassed clients through the unfiltered instance. **UI** (M8.1a2b2): `/networks` has a DNS queries card under DNS filtering while the latest revision has blocking and statistics on: 24 h, 7 days or 30 days of totals (queries, blocked, the blocked share, clients), the queries as stacked bars (answered and blocked; by hour over 24 h, by local day otherwise), the busiest clients (linking to their page, and to their queries) and the top answered and top blocked domains of the last 24 h, read every minute. Admins allow a blocked domain or block an answered one from there or from the query log, as the next revision (it reaches the gateway with an apply); a domain the allow or deny list already covers says so. The query log (a dialog) filters by client, outcome and domain text and reads older pages on demand.

## IPv6

- The gateway gets a delegated prefix (DHCPv6-PD) or uses 6rd, then hands out a /64 per network (`ip6assign`, with `ip6hint` set to the VLAN ID in hex).
- An `fdxx::/48` ULA is always present for stable local addressing.
- RA/SLAAC by default; stateful DHCPv6 optional.
- The IPv6 firewall mirrors the IPv4 policy.

## Firewall policy [M4.2] (D-079)

- One zone per network, plus wan.
- Inter-network policy is a matrix (from → to: allow | block), seeded by purpose; `firewall.policies` override cells. Replies to connections the other side opened always pass (fw4 accepts established traffic in every direction), so a blocked cell whose reverse is allowed is "replies only"; the model's `established` action renders as block.
  - LAN and Management → everything: allow.
  - IoT → LAN: block (replies pass). IoT → internet: allow.
  - Guest → internet only; Guest → gateway: DHCP and DNS only (the zones that don't reach the gateway get `Allow-<zone>-DHCP`/`-DNS`, and with IPv6 `-DHCPv6`/`-ND`).
- **Port forwards** (`firewall.forwards`, DNAT): a unique name (not `DMZ`), on or off, TCP, UDP or both, a WAN port or range, the host (an address in a network's subnet, not the gateway's, the subnet's or its broadcast) and its first port when it differs (a range keeps its length), an optional source subnet, and NAT reflection (on by default: hosts on the networks reach the forward through the WAN's address too). Enabled forwards may not share a port and protocol. Forwards behind DS-Lite or an IPv6-only WAN warn: the internet can't reach them over IPv4.
- **DMZ host** (`firewall.dmz`): every connection from the internet that no forward claims goes to one host.
- **UPnP IGD and NAT-PMP/PCP** (`firewall.upnp`, miniupnpd): on for the main LAN on new sites (off on migrated ones, as before), for the networks chosen. Secure mode (a client maps ports only to itself), ports from 1024 only (OpenWrt's stock permissions). The live list of mappings comes from miniupnpd's lease file with the gateway's DHCP leases (the `leases` set, every minute).
- Custom traffic rules (protocols, ports, IP sets) and time-based rules for parental schedules [M8.1]; IP/geo blocklists using nft sets (backlog). IPv6 "forwards" (opening a host's port to the internet) come with custom rules.
- Rendering: fw4 UCI (`zone`, `forwarding`, `rule`, `redirect`; `ipset` later), validated with `fw4 check` in the system harness. Each forward is a `redirect` from `wan` to the zone of the network whose subnet holds the host, with `target`, `dest_port` and `proto` always written; the DMZ is the last redirect (`name 'DMZ'`, `proto 'all'`, as LuCI writes it). UPnP is the `upnpd` package (miniupnpd's stock options and permission rules, `internal_iface` naming the networks), which needs `miniupnpd-nftables` (installed by the apply, D-076) and carries over the `uuid` miniupnpd writes on its first start; untrusted zones it serves get `Allow-<zone>-UPnP` (UDP 1900 and 5351) and `Allow-<zone>-UPnP-HTTP` (TCP 5000).
- Import: named DNAT redirects from `wan` to a host on a network become forwards (`DMZ` without ports the DMZ host); unnamed ones, ranges that change length and the like stay raw sections. miniupnpd's package becomes `upnp` (on unless `enabled '0'`; off without the package).
- UI (M4.2b2): the `/security` page. **The matrix** has a row per network and a column per other network plus Internet (the internet's row stays out: forwards are the way in); a blocked cell whose reverse is allowed reads "Replies only", and cells that differ from the purpose's seed are marked. Admins toggle cells and save them as one revision: cells left as they were keep their policies (an `established` one too), changed cells get a policy only where they differ from the seed, and cells of a network another save added stay. **Forwards** open in a dialog that checks what the server checks (names, ports, the host on a network, clashing enabled forwards, the source as an address or subnet, a bare address becoming a /32) and suggests the clients' addresses; forwards are keyed by name across revisions. **The DMZ host** is set or removed inline. **UPnP**: on or off and its networks (those with IPv4), a hint while the gateway doesn't manage `upnpd`, and the open ports with the client's name. A network can't be deleted while UPnP, a forward or the DMZ host uses it; deleting one drops the policies naming it.

## VPN [M8.2] (D-140)

- A WireGuard server on the gateway. Peers get auto-assigned addresses (default 10.0.250.0/24), a QR code or `.conf` download, and full or split tunnel routes.
- The DDNS hostname is the endpoint. Handshake and traffic stats are shown per peer.
- Site-to-site peers; optional management of the Tailscale package.
- **Document** (schema v17): `vpn.wireguard`, absent until set up: on/off, the UDP port (51820), the gateway's tunnel address with the subnet's prefix (10.0.250.1/24), the endpoint (a DDNS entry by id, or a host typed in), whether peers use the gateway's DNS, the server's keypair (private key in the vault, public key plain), and its peers. A peer has an id (`[a-z][a-z0-9_]{0,11}`, never changed), a name, on/off, an address in the tunnel, a public key, a preshared key and, where the controller made the keypair, its private key (both in the vault); it is a **client** (full or split tunnel) or a **site** (the networks routed to it, and optionally where the gateway dials it).
- **Keys:** the controller generates the server's keypair, every preshared key, and a peer's keypair unless the peer brings its own public key; the private keys stay sealed in the vault, so a peer's configuration can be shown again. A save (and a file import) makes what is missing: the server's keypair when it has no private key, a peer's when it has neither a private nor a public key, a preshared key for every peer without one. **Public keys follow private keys:** a private key the latest revision holds keeps that revision's public key, any other has it derived again (X25519), so no document pairs a private key with another public key; a peer switches to its own keypair by clearing its private key (`null` in the save's secrets) and giving its public key. A file imported without the keys gets new ones (*generated*; lifecycle.md, Site import).
- **Peer configuration** (`POST /api/v1/vpn/wireguard/peers/{id}/config`, admins, audited as revealing a secret): the latest revision's `.conf` for the peer (`file_name` `<id>.conf`, `conf`, `own_key`), which the UI also shows as a QR code. `[Interface]`: its private key (a comment instead where it brought its own), `Address` its /32, for a client `DNS` the gateway's tunnel address when `dns`, for a site its `ListenPort` where the gateway dials it. `[Peer]`: the server's public key, the preshared key, `Endpoint` the DDNS entry's hostname or the typed host (an IPv6 address in brackets) and the port, `AllowedIPs` (a full tunnel `0.0.0.0/0, ::/0`; a split tunnel and a site: the tunnel's subnet, the networks the `vpn` zone reaches in the matrix, and the other enabled sites' networks), `PersistentKeepalive = 25`. 404 for an unknown peer; 409 while the server has no keypair or its DDNS entry is gone.
- **Status** (`GET /api/v1/vpn/wireguard/peers`, any user; M8.2a1b2): the gateway's `services` set reads `wg show vpn dump` every minute, through a pipe (the private and preshared keys that start its lines never reach a file or the controller), into its facts (`services.wireguard`: the node's clock, the tunnel's public key and port, and each peer's public key, endpoint, latest handshake and rx/tx bytes; `null` without the device). The endpoint lists the latest revision's peers matched by public key: `on_gateway` (`false` until the revision that adds the peer, or its key, is applied), `connected` (a handshake within 3 minutes of the collection, WireGuard's reject-after time), the handshake moved onto the controller's clock, the endpoint and the traffic; with whether the gateway is online, when its facts were collected, whether the tunnel runs, and whether it runs with the revision's server key (`key_applied`). The sim's gateway answers for the tunnel its `network` file sets up: site peers and two client peers of three connected, the third seen three hours ago or never, all from their keys.
- **Tailscale** (schema v18; M8.2a2): `vpn.tailscale`, absent until set up, on the gateway only (the package is 24–29 MB installed): on/off, the networks it advertises as subnet routes (by id; each needs an IPv4 subnet), whether it offers itself as an exit node, its machine name (one DNS label; the gateway's hostname where none), and an auth key (`tskey-…`, sealed in the vault at `vpn/tailscale/auth_key`) it logs in with by itself; without one, an admin opens the login URL the gateway hands out. **Render** (while on): the `tailscale` zone over `tailscale0` (`list device`; no netifd interface: the daemon makes the device), trusted like `vpn`, its own matrix row seeded like the default LAN's and editable through the policies; `Allow-Tailscale` on the WAN for UDP 41641 (direct connections rather than relays); the `tailscale` package installed where missing. The daemon's prefs (routes, exit node, name) aren't UCI: the engine sets them (below). **Prefs, login & API** [M8.2a2b]: the agent's `tailscale` op drives the CLI: `set` (logged in or not), `up` (`--reset`, after a `down`), `down`, `logout` (the prefs stay), and `login`. Every action but `down` and `logout` passes all the prefs: the routes, `--advertise-exit-node`, `--hostname` (empty: the gateway's hostname), `--accept-dns=false` (dnsmasq stays the gateway's DNS), `--accept-routes=false` and `--netfilter-mode=off` (fw4 is the only firewall: tailscaled's own input rule drops 100.64.0.0/10 from every other interface, which would cut a CGNAT WAN off; its SNAT of subnet traffic goes with it, so LAN hosts see tailnet addresses and answer through the gateway, their default route). `tailscale login` resets every pref it isn't given, hence all of them each time. A login with the auth key passes it as a file of root's (`--auth-key=file:`, removed when the CLI ends), never in argv; a login without one starts the CLI in the background and answers the URL `tailscaled` hands out (it keeps it in `status --json` while the login waits, after the CLI gives up), or the URL already waiting; a daemon logged in gets none. The `services` set adds `prefs` from `tailscale debug prefs` (whether it should run and is logged out, the advertised routes, the name, DNS and routes taken, netfilter off). **Engine** (`TailscaleSync`): every 30 s and on each `services` collect it compares the saved site with the managed gateway's facts, like the LEDs schedule (90 s to settle, 10 min before the same request again, a gateway a job holds left alone): prefs that differ get `set`; Tailscale off in the site gets `down` while the daemon wants to run; a stopped daemon still logged in gets `up`; a logged-out one logs in with the auth key from the vault, if the site has one (else it waits for an admin). A site without `vpn.tailscale` leaves the daemon alone, as does an observed gateway. A refusal raises `tailscale_failed` (`node:<id>/tailscale`, with the CLI's words), cleared by `tailscale_ok`. **API:** `GET /api/v1/vpn/tailscale` (any user: the daemon from the facts, `prefs_applied`, and `unapproved_routes`, the site's routes and exit node (`0.0.0.0/0`) the tailnet's admin hasn't approved yet, while it runs); `POST …/login` (admins, audited as `tailscale`: the login URL and the state; 409 while the site has Tailscale off, the gateway is observed, offline, held by a job or doesn't run the package yet, 502 with the CLI's words); `POST …/logout` (admins, audited; with an auth key in the site the engine logs it in again, so turning Tailscale off is how to keep it out). **Sim:** the gateway's daemon takes the op: an interactive login's URL is opened by the demo's admin 20 s later, a key logs in at once (one with `invalid` in it is refused), and logged in it runs in a demo tailnet with two peers and its routes approved. **Status:** the `services` set reads `tailscale status --json` through a pipe into `services.tailscale` (state, version, tailnet and MagicDNS suffix, the gateway's name, addresses and approved routes, health warnings, and up to 200 peers, online first), never the login URL, which would let any user who sees the facts join the gateway to their own tailnet; `null` without the package, a `null` state while the daemon is stopped. **Checks:** routes name networks with an IPv4 subnet, once; no network is named `tailscale`; no UDP forward or WireGuard takes 41641 while it is on.
- **Checks:** the port isn't one a UDP port forward takes; the tunnel's subnet (/16 to /30, private) overlaps no network, CGNAT, 192.168.1.0/24 or a static WAN, and IPAM keeps it free for new networks; no network is named `vpn`; peers' ids, names, addresses and public keys are unique (the server's key too); a site's networks (up to 16) overlap no network, the tunnel or another site's.
- **Render** (gateway only, while on; `network` and `firewall`): `interface vpn` (`proto wireguard`, the key, `listen_port`, `addresses`); `wireguard_vpn` `wg_<id>` per enabled peer (its /32 and a site's networks in `allowed_ips`, `route_allowed_ips` and a 25 s keepalive for a site, its endpoint where set); the `vpn` zone (trusted, like the default LAN's), its matrix row seeded like the default LAN's (it reaches every network and the WAN; the trusted networks reach it), editable through the policies; `Allow-WireGuard` on the WAN for the port. `wireguard-tools` is installed where missing. A server that is off renders nothing. Brownfield tunnels stay raw sections.
- **UI** [M8.2b1] (`/vpn`, a sidebar page of its own after Security; Tailscale below it since b2): the **WireGuard server** card (its state on the gateway: off, no report yet, gateway offline, not running until applied, running on an older key, running; what peers dial, the tunnel, DNS, the server's public key to copy) and the **Peers** card (each peer's address and role, an *Own key* badge, its state from `GET v1/vpn/wireguard/peers`, refreshed every 30 s and on each new revision or apply: connected with the handshake's age, the last handshake, never connected, not on the gateway yet, the tunnel down; where it dials from and its traffic). Admins set the server up and edit it in a dialog (port, the gateway's tunnel address, a DDNS name or a host, the gateway's DNS, on/off; removing it drops every peer and the `vpn` zone's policies), add and edit peers (a name, the next free address, a phone or laptop with a full or split tunnel, or another site with its networks and optionally where the gateway dials it; its own public key instead of keys made by uniwrt; on/off; delete), each a save checked as the model checks it, with the server's issues on their fields. A new peer's id comes from its name (whole words, up to 12 characters). *Save and show configuration* opens the peer's configuration (`POST …/config`): its QR code for the WireGuard app, the `.conf` to copy or download, and a note when the peer brought its own key. The firewall matrix on `/security` gains the `vpn` row and column while a server is set up (and `tailscale`'s while Tailscale is).
- **Tailscale UI** [M8.2b2] (`/vpn`, below WireGuard): the **Tailscale** card (its state from `GET v1/vpn/tailscale`, refreshed every 30 s and on each new revision or apply: off, no report yet, gateway offline, not on the gateway until applied, the daemon not answering, logged out (with the saved auth key, logging in by itself), waiting for the tailnet admin's approval of the device, stopped, starting, connected, or running without reaching Tailscale's servers; the tailnet, machine name, addresses, advertised networks, exit node and version; *uniwrt is putting the saved settings on the gateway* until `prefs_applied`; the routes awaiting approval, the exit node by name, with a link to the admin console; `tailscaled`'s health warnings; a note on an observe-mode gateway; on a 24.10 gateway, that its package sends the daemon's logs to Tailscale) and, while it runs, **Tailnet devices** (each peer's first address and OS, online direct or relayed, or when last seen, its traffic; *Showing n of m* beyond the 200 listed). Admins set it up and edit it in a dialog (the networks with an IPv4 subnet to advertise, the default ones for a new setup; the exit node; the machine name; the login: *From this page* or *With an auth key*, a password field whose value goes in the save's secrets, empty keeping a saved key, and switching back clearing it; on/off; notes on the package's 25–30 MB and the 24.10 log upload; *Remove Tailscale*, which drops the zone's policies and leaves the daemon as it is), each save checked as the model checks it. *Log in* (while logged out) opens a dialog that starts the login (`POST …/login`, audited) and shows the URL as a link and a QR code, reading the status every 5 s until the gateway reports it runs (*Logged in to …*), or says it needs none; *Log out* asks first, warning that a saved auth key logs it in again.

## Other services [M8.1]

- **DDNS** [M8.1a1, D-132] (`services.ddns`, ddns-scripts on the gateway): up to 16 names, each with an id (its `ddns.service` section), a hostname, IPv4 (an A record from `wan`) or IPv6 (AAAA from `wan6`), the address from the WAN interface or from a web echo (`api.ipify.org`/`api6.ipify.org`, for a gateway behind another router), and a provider: Cloudflare (zone, API token; `cloudflare.com-v4`), DuckDNS (`<name>.duckdns.org`, token), deSEC (token), No-IP and Dynu (username, password), FreeDNS (afraid.org v2 token), or a custom update URL (`[DOMAIN]`, `[IP]`, `[USERNAME]`, `[PASSWORD]`; a password only where the URL names it). The token or password is a vault secret (`services/ddns/<id>/secret`). Updates go over HTTPS (except a custom `http://` URL, which warns when it carries the password) against the CA bundle; the address is compared every 10 minutes and sent anyway every 72 hours; private addresses are never published; notices and errors go to syslog. Render requires `ddns-scripts` and `ddns-scripts-services`, plus `-cloudflare` or `-noip` while such an entry runs. The `services` collect set reports each name's registered address, last update and whether its updater runs, and the running DoH instances.
- **NTP server** [M8.1a1] (`services.ntp_server`, on for new and migrated sites): the gateway answers NTP on its networks, and pools without NTP servers of their own hand it out (option 42, `0.0.0.0`: dnsmasq's own address). Brownfield import keeps a gateway's `enable_server` as it is (stock OpenWrt has it off).
- **mDNS reflection** [M8.1b1, D-136] (each network's `mdns`; on for new networks but guest and management ones): the gateway's `mdns-repeater` (21 KiB, UCI package `mdns_repeater`, section `main`, `list interface` of the networks' devices) repeats IPv4 mDNS between the networks that have it on and an address on the gateway, while there are two or more; at most 5 (the repeater's limit: validation refuses more). It runs only on the gateway (render requires `mdns-repeater`, service `mdns-repeater`); with fewer than two networks a gateway that holds the package keeps its section without interfaces, the service off. The untrusted zones among them get a rule to reach it (`Allow-mDNS-<network>`: UDP 5353 to 224.0.0.251); the default and management networks reach the gateway anyway. The repeater loses its group membership when netifd makes a device anew (a network restart), and its init script's triggers name devices where netifd expects interfaces, so the controller's footprint carries an interface hook (`/etc/hotplug.d/iface/90-uniwrt`) that restarts it when one of its devices comes up. Import reads which networks it serves from the package (none without it). Nodes that managed `dhcp` before schema v15 manage `mdns_repeater` too.
- **IGMP snooping and multicast to unicast** [M8.1b1, D-136]: a network's `igmp_snooping` turns snooping on for the bridge every network shares (netifd's `igmp_snooping` on `br-lan`; one network's on is on for all). netifd then converts multicast to unicast on every bridged AP interface by default (`multicast_to_unicast`, with hairpin): each WLAN has **Multicast to unicast** (schema v15, on), rendered as `multicast_to_unicast '0'` only when off, for clients that miss such frames; import reads it.
- **Wake-on-LAN** [M8.1b2a1, D-137]: an admin's `POST v1/clients/{mac}/wake` (a client the controller knows; audited `wake_client`) has the gateway send the magic packet with `etherwake -b -i <device>` (EtherType 0x0842 to the broadcast address, so a bridge's stale entry can't misdirect it): on the gateway's device of the client's last IPv4 subnet, else the one its lease or neighbor entry names, else on every network the gateway serves (a static address without a gateway). Stock images have no sender (no `ether-wake` applet, a TCP-only `nc`, no ucode socket module), so a **managed** gateway without it gets `etherwake` (6 KiB) from the feeds first (index refreshed, then installed; up to 5 min, answered when done: `installed` in the outcome, ✅ 24.10 opkg and 25.12 apk); an observed one is refused with a hint, unless it has it already. Refused while a job holds the gateway, or while it is offline. Answers `WakeOutcome` (`node`, `devices`, `installed`). **UI** [M8.1b2a2]: *Wake* in a client's header (admins) asks first, says while it waits that the first wake may take a minute or more (the install), keeps a refusal in the dialog in the server's words, and toasts where the packet went.
- **Restarts** [M8.1b2a1, D-137]: an admin's `POST v1/reboots` (`{"nodes": [...]}`; 202 with the job; audited `reboot`) restarts **managed** nodes (409 for one in observe mode) one at a time, as an apply orders them (farthest from the gateway first, the gateway last): `reboot` → down within 1 min → a login with its pinned host key within 10 min → if it was never seen down, an uptime shorter than the time since the command. The first node that fails ends the job, leaving the rest as they are. **UI** [M8.1b2a2, D-137]: *Restart* in a device's header (admins; disabled with the reason in observe mode or offline; *Restarting…* while a restart includes it) and *Restart…* in the devices list's toolbar (disabled until a device is managed), one dialog (`features/devices/reboot`): several devices are picked (gateway last, observed ones disabled, offline ones unchecked), one is asked about; it warns that each is offline a few minutes, that the gateway takes the internet with it, and that the first failure stops the rest; then follows the job on the `jobs` topic (each device Waiting → Restarting → Back, with how long it took), as it does a restart of the same devices started elsewhere.
- **Scheduled restarts** [M8.1b2b1, D-138] (schema v16 `schedules.reboot`: days of the week and a time, or none; off for new and migrated sites): run by the controller on the **saved** site (no apply), in the site's time zone, on **managed** nodes only. Each node follows the site's time (`reboot: site`, the default), never restarts on a schedule (`never`), or has days and a time of its own (`own`). Every minute the server gathers the nodes whose time came within the last hour and starts one restart job of them (D-137's: farthest first, the gateway last, recorded as a job without a user), none while another scheduled restart runs. A node offline or held by a job waits within its hour; one the hour ends on unrestarted raises `scheduled_reboot_missed` (offline, busy, or the job stopped before it), as does each node a failed job left as it was. A node is tried once per window (in memory; after a controller restart, an uptime shorter than the time since its window opened counts as done, and a node tried in the last 20 h isn't tried again, so a repeated daylight-saving hour can't restart it twice). Nothing restarts while the controller is down or the time zone can't be read. **UI** [M8.1b2b2]: Settings › Site › **Schedules** (admins; viewers read it): restarts on or off, the days and the time, the next restart in the site's zone, and the managed devices that follow it (a device's own time named beside it); a device's Config tab › **Schedules**: the site's, never or its own (days and a time, starting from the site's), the next restart, and the latest missed one of the last 8 days with why. Both save the next revision and say it needs no apply (nothing in the devices' configuration changes).
- **LEDs schedule** [M8.1b2b1, D-138] (schema v16 `schedules.leds_off`: weekly spans as WLAN schedules, or none; each node's `led_schedule`, on): while the schedule is on, the managed nodes that follow it have **every LED** dark; after it, they come back as they were. The agent's `leds` op does it without UCI: `off` saves each LED's trigger, brightness and the trigger's settings (its writable files, and those of a subdirectory such as usbport's `ports/`) to `/var/run/uniwrt/leds.json`, then sets `none` and 0 (an LED found lit again is saved anew); `on` puts back the trigger, then its settings, then the brightness of one without a trigger, and forgets them (an LED that fails stays saved, and the op fails naming it). The `system` set reports `leds` (how many, how many lit, whether a state is held). The engine compares every 30 s and on each `system` collect, like WLAN schedules (45 s to settle, 10 min before the same request again, nodes a job holds left alone): lit LEDs inside the schedule get `off`, a held state outside it gets `on`. A reboot brings the LEDs back (the state in `/tmp` is gone) until the next comparison; while the controller is down they stay as they are. A refusal raises `led_schedule_failed` (`node:<id>/led-schedule`), cleared by `led_schedule_ok`; the schedule turning isn't announced. **UI** [M8.1b2b2]: the same two cards: the site's LEDs-off spans (WLAN schedules' editor; a new one starts every day 23:00–07:00) and who follows them; per device, whether it follows them (with the site's spans in words), its LEDs now from the `system` set (how many lit, and whether the controller holds them off) and, while its latest LED event is `led_schedule_failed`, the refusal.
- **Package manager** [M8.1b3, D-139]: per node, install, remove and upgrade packages from the node's own feeds; packages the node needs are locked. **Engine & API** [M8.1b3a]: `GET v1/nodes/{id}/packages` (`NodePackages`: the inventory as last read, each package with its `lock` and whether it comes `with_firmware`; `required_unknown` says why the site's requirements can't be told, as when the configuration doesn't render or the facts aren't read yet: until then nothing counts as required and nothing can be removed). A package is locked `required` when render requires it on the node for the latest revision (as an apply installs it, D-076), `essential` when `model::packages::essential` lists it (the base system, dropbear, ucode and its modules, the package manager, netifd, procd, ubus, uci, firewall4 and nftables, dnsmasq and odhcpd, the kernel and every kmod, the CA bundle, uclient-fetch and its TLS; on a node with radios its wpad, hostapd, iw and iwinfo; batctl while the site meshes; on the gateway ppp, ds-lite and 6rd); the kernel, kmods, `base-files` and `libc` are upgraded only with the firmware. Admins: `POST v1/nodes/{id}/packages/catalog` (`PackageCatalog`, managed nodes: the index refreshed, then `apk query --available` or opkg's lists, with name, version, installed size and description, and the upgrades on offer from `apk query --upgradable` or `opkg list-upgradable`) and `POST v1/nodes/{id}/packages` (`PackageChanges`: `install`, `remove`, `upgrade`; 202 with the job; 409 in observe mode; 422 for a malformed name, `[a-z0-9][a-z0-9._+-]*`, none, or a locked one; audited `packages`). The `packages` job: connect → check (the names against what is installed, the locks, then the index refreshed and a dry run of each change, `apk del|upgrade|add -s` or `opkg remove --autoremove|upgrade|install --noaction`: refused with nothing changed when a removal would take a locked package along or leave a named one because another needs it, an upgrade pulls in a firmware package, or the new packages, plus an upgrade of one that `/rom` holds, need more flash than the overlay has free less a reserve of a tenth of it, at least 1 MiB) → install (removals, then upgrades, then installs, one command each; a package's postinst enables and starts its service; the first failure ends it, saying what changed before) → inventory (read again and kept, also after a failed install). Packages aren't configuration: nothing rolls back, and the site's revision is untouched (a firmware upgrade carries over the packages installed on purpose, D-121). The sim answers every command for apk and opkg (`sim::render::packages`: extra feed packages with a dependency, newer versions of image packages, `/rom`). **UI** [M8.1b3b]: the device's Config tab, *Installed packages* (`features/devices/software`): the inventory as last read (count, package manager, when), searched by name, on purpose or as dependencies (on purpose at first), each lock and `with_firmware` as a badge whose hint says why; observe mode and viewers read only. On a managed node admins tick removals in the list (locked ones can't be ticked, nor any while `required_unknown` says why, which the card shows) and pick upgrades and installs in *Add or upgrade…*, a dialog that reads the catalog when first opened (saying that the index refresh can take a minute), keeps it until the packages change, and offers *Read again*: the upgrades on offer (a firmware one can't be chosen) and the feeds' packages not installed, searched by name and description (names first). A package is removed or upgraded, not both. The chosen changes wait on the card (*Review changes…*, *Clear*); the confirmation lists every one (removals with their version, upgrades from → to, installs with version and size, their flash in all), says the dry run comes first and that a new package's service starts at once with nothing rolled back, then starts the job and follows it on `jobs` (the Check step's detail names what the dry run adds and removes). The list is read again as each `packages` job on the node ends, and the chosen changes it made moot are dropped (all after a success).
