# AGENTS.md

This is the entry point for AI coding agents working on **uniwrt**. Claude Code loads it through `CLAUDE.md`. Because it is in every session's context, it stays short; everything else is read on demand.

**uniwrt** is a UniFi-class controller for OpenWrt mesh networks: one static Rust binary with an embedded SolidJS UI, shipped as a `FROM scratch` multi-arch container. It adopts OpenWrt routers (a gateway plus mesh APs), manages them individually or as a fleet, visualizes the network, and troubleshoots it. Repo: https://github.com/robertzas/uniwrt

## Standing directives (from the owner; always apply)

1. **Quality and performance come first. Context and token economy come second.** Never trade correctness, safety, UX or runtime efficiency for fewer tokens.
2. **Checkpoints (prompt-cache aware).** A checkpoint is a point where the context could be cleared without hurting quality: the WP is done, docs are updated, everything is committed and pushed, and CI is green. Only the owner can clear context, so at a checkpoint decide with "Clear or keep" (under Token economy rules):
   - **Clearing pays off:** stop, and end the reply with
     `✅ Checkpoint — /clear recommended (<why>). Next: <WP id + title>. After clearing, say "continue".`
   - **Keeping is cheaper:** continue into the next WP without stopping (the owner's choice, D-024). If you must stop anyway, end with
     `✅ Checkpoint — keep context (<why>). Next: <WP id + title>. Say "continue" within 1 h; after that, /clear first.`
   - **Mid-WP:** apply the same test when a long context starts to hurt quality, or when the owner will be away for more than an hour (the cache expires). Make `docs/STATUS.md` carry the state before you stop.
3. **Offer options.** Whenever you have a good idea, a suggested change or a recommendation, give the owner 2–4 options with a recommended default (use AskUserQuestion in interactive sessions), then record the outcome in `docs/DECISIONS.md`. For small, reversible implementation details, decide and note it.
4. **Keep the docs true.** README.md, AGENTS.md and `docs/` capture every directive, the plan and all decisions. Update them in the same commit as the change that would make them stale.
5. **Commit every significant change** using Conventional Commits, directly on `main` (the owner's choice). Every push to `main` builds, tests and releases (see `docs/dev/BUILD.md`), so run `just check` before pushing and keep `main` green.
6. **Principal distribution:** a `FROM scratch` image plus static musl binaries for x86_64, x86 (i686), arm32 (armv7) and arm64. No runtime dependencies: the UI, CA roots, tzdata and the SSH client are all embedded.
7. **Product bar:** feature-rich enough that the owner never has to log into an individual router; a very professional, modern, impressive UI; efficient on small hardware; scales to any number of nodes (reference deployment: 1 gateway + 3 APs).
8. **Never brick a live network.** Node changes are transactional with automatic rollback. Nodes start read-only (observe mode) until management is explicitly enabled.

## Session protocol

1. **Start:** read `docs/STATUS.md`. It names the current work package (WP) and the docs to load. In `docs/ROADMAP.md`, read only that WP's milestone section: run `grep -n '^## M' docs/ROADMAP.md`, then Read with offset/limit.
2. **Locate code** with `docs/MAP.md` (generated by `just map`) and grep. Read a crate's contract (the `//!` header in `lib.rs`) before its implementation.
3. **Work** on one WP and write tests alongside the code. If the WP outgrows the session, split it in ROADMAP.md and checkpoint.
4. **Finish:** fold in the open, green Dependabot updates (D-030) → run `just check` → tick the WP in ROADMAP.md → rewrite `docs/STATUS.md` (≤ 40 lines) → commit → push → confirm CI is green → checkpoint (directive 2): stop for a `/clear`, or continue into the next WP.

## Token economy rules

- Load docs progressively: AGENTS.md (automatic) → STATUS.md → the WP's section → only the feature and dev docs the WP lists.
- Prefer contracts, maps and specs over implementation. Grep for symbols, and read line ranges instead of whole large files.
- Never read generated or bulky files: `Cargo.lock`, `web/bun.lock`, `web/src/api/gen/**`, `web/dist/**`, `target/**`, `crates/*/data/oui*`, and `**/*.snap` unless you are reviewing that snapshot.
- Use quiet commands: `just check` (summarized output), `cargo nextest run --status-level fail`, `gh run view --log-failed`.
- Don't re-read what is already in context and unchanged, including files you just wrote: a re-read is paid again. Batch independent tool calls. Write new files in one pass.
- Keep source files to about 400 lines or fewer, with one concept per file, so targeted reads stay cheap.
- Extend through data where possible (ISP presets, log patterns, collectors, alert rules): each addition is one small file.
- Record a decision once, in DECISIONS.md. Never reopen an accepted decision without the owner.

### Prompt-cache cost model

The owner runs Claude Code on Opus 5.5 with a 1-hour cache TTL; prices are in D-024. Relative to fresh input (1×):

- Context that is already cached costs **0.05×** per request, and every request (each tool round trip) re-reads all of it. Batching saves more as the context grows.
- New tokens (tool output, replies, re-reads) are written to the cache once at **2×** (1.25× when the TTL is 5 minutes, as in usage overage), then carried at 0.05× by every later request.
- Output, thinking included, costs **5×**: prefer targeted edits to rewriting whole files, and keep replies tight.
- When the TTL passes without a request, the cache expires and the next request re-writes the whole context at the write price.

### Clear or keep

Keeping costs 0.05 × D per request, where D is the context the next work won't use. Clearing costs about 2 × R once, where R is what the next work must load again (STATUS.md, the WP section, specs, code) plus some re-orientation, typically 20–30k tokens. Clear when D × (requests ahead) > 40 × R; 40 is the write price over the read price (25 with the 5-minute TTL). With R ≈ 25k:

| Work ahead | Clear when the unused context exceeds about |
|---|---|
| A follow-up (~10 requests) | 100k |
| A small WP (~50 requests) | 20k |
| A full WP (100+ requests) | 10k |

- When the next WP reuses most of what is loaded, D is small and keeping usually wins.
- After a gap longer than the TTL the cache is cold, so keeping means re-writing all of the context: clear unless most of it is still needed.
- Estimate sizes from what you loaded: roughly 1k tokens per 4 KB of text or per 100 lines of code.
- Quality outranks cost (directive 1): keep when the next WP depends on details that STATUS.md can't carry, and clear when a long context starts to blur details, whatever the table says.

## Conventions (summary; details in docs/dev/CONVENTIONS.md)

- Rust: edition 2024, thiserror in libraries and anyhow in the binary, no `unwrap` outside tests, `tracing`, clippy with `-D warnings`. Pure crates use no tokio and do no IO.
- Web: strict TypeScript, Biome, Solid with Tailwind tokens and Kobalte primitives. Features never import other features.
- Node side: ucode or POSIX sh, JSON lines on stdout, argv arrays (never interpolate values into shell strings), feature-detect modules.
- Commits: `type(scope): summary`, where type is one of feat, fix, perf, refactor, docs, test, build, ci, chore. Mark breaking changes with `!`.

## Definition of done (per WP)

Acceptance criteria are met · tests are added and `just check` is green · docs are updated (spec, ROADMAP tick, STATUS) · decisions are recorded · the work is committed and pushed · CI is green on `main` (check with `gh run list` or `gh run watch`) · the checkpoint decision is made (directive 2).
